# 公网上线前必须完成

本文档是生产发布门禁。三项全部完成并验证前，不得将域名解析到公网，也不得临时关闭生产安全校验绕过启动失败。

管理员用户名、密码、私有登录路径及生产密钥不写入本文档。它们只保存在本机被 Git 忽略的 `.secrets/production-auth.txt`，复制到服务器密码管理器或受保护的环境文件后，应限制为仅部署账号可读。

## 门禁一：由 PostgreSQL 表所有者完成迁移

### 原因

当前应用数据库账号是 `cappa_rw`，`users` 表所有者是 `postgres`。应用账号可以读写业务数据，但没有也不应该获得 `ALTER TABLE` 或表所有权。

生产登录需要 `users.auth_version` 撤销旧 JWT 和会话。缺少该列时，生产进程会拒绝启动。

### 操作

1. 备份生产数据库，并验证备份文件可读取。
2. 在维护窗口暂停 Web、Celery worker 和调度器的写入。
3. 使用 PostgreSQL 表所有者或专用迁移账号运行完整 Alembic 迁移：

   ```bash
   cd /path/to/dig_ytb_channel/src/backend
   /path/to/venv/bin/flask --app app:create_app db current
   /path/to/venv/bin/flask --app app:create_app db upgrade
   ```

   运行命令的环境必须是 `FLASK_ENV=production`，并通过服务器密钥管理机制注入生产配置和迁移账号的 `DATABASE_URL`。不要把数据库密码直接写在命令行或终端历史中。

4. 验证列和迁移版本：

   ```sql
   SELECT column_name, data_type, is_nullable, column_default
   FROM information_schema.columns
   WHERE table_schema = 'public'
     AND table_name = 'users'
     AND column_name = 'auth_version';

   SELECT version_num FROM alembic_version;
   ```

5. 确认 `auth_version` 为非空整数、默认值为 `1`，再恢复服务。

对应迁移文件：`src/backend/migrations/versions/20260716_user_auth_version.py`。

### 验收

- [ ] 数据库已备份并完成恢复抽查。
- [ ] 迁移由表所有者或专用迁移账号执行成功。
- [ ] `users.auth_version` 已存在，现有用户值均不为空。
- [ ] 应用账号仍然没有建表、改表或表所有权权限。
- [ ] 生产应用通过启动时数据库结构校验。

## 门禁二：轮换历史密钥并清理 Git 历史

### 原因

`.env.bak` 和 `scripts/deployment/production.env` 曾被 Git 跟踪。工作区删除文件只能阻止继续使用，不能清除已有提交、克隆、CI 缓存或备份中的值。因此旧值必须全部作废。

### 先轮换，再清历史

按以下清单逐项在对应服务控制台生成新值、更新服务器秘密、验证新值生效，然后撤销旧值：

- [ ] PostgreSQL 应用账号密码及其他数据库连接凭据。
- [ ] `SECRET_KEY`、`JWT_SECRET_KEY`、`LOGIN_PORTAL_TOKEN`。
- [ ] YouTube API key、Google API key、Gemini key。
- [ ] Google OAuth client secret 和刷新令牌（如有）。
- [ ] Bilibili `SESSDATA`、`bili_jct`、Cookie、设备标识等会话凭据。
- [ ] Reddit client secret、访问令牌（如有）。
- [ ] Redis 密码或连接凭据（如生产 Redis 启用了认证）。
- [ ] 旧管理员密码以及其他仍然活跃的测试账号密码。

轮换 `SECRET_KEY` 和 `JWT_SECRET_KEY` 会让现有登录会话失效，这是预期行为。

### Git 历史清理

这一步会改写共享历史，必须先冻结推送、备份仓库并通知所有协作者。建议由仓库管理员在单独维护窗口执行：

```bash
git log --all -- .env.bak scripts/deployment/production.env

# 安装并确认 git-filter-repo 后，在仓库镜像或已备份的维护副本中执行：
git filter-repo --force \
  --path .env.bak \
  --path scripts/deployment/production.env \
  --invert-paths

# 审核改写结果后，再由仓库管理员更新远端分支和标签。
```

不要在未经协调的日常工作副本中直接 force push。远端历史更新后，所有协作者和部署目录应重新克隆，不应继续使用旧工作副本做普通 pull。

### 验收

- [ ] 上述旧凭据已全部撤销，而不只是从文件中删除。
- [ ] 新凭据只存在于密码管理器、服务器 secret 或 0600 环境文件。
- [ ] CI/CD 日志、制品、缓存和服务器备份已检查。
- [ ] Git 远端历史已清理并由第二人复核。
- [ ] 所有协作者和部署环境已重新克隆。

## 门禁三：配置真实域名、TLS、CORS 和 Nginx

### 生产环境文件

在服务器上复制 `.env.production.example` 为 `.env.production`，权限设为 0600：

```bash
cp .env.production.example .env.production
chmod 600 .env.production
```

至少必须替换：

- `SECRET_KEY`
- `JWT_SECRET_KEY`，且必须与 `SECRET_KEY` 不同
- `LOGIN_PORTAL_TOKEN`
- `DATABASE_URL`
- `REDIS_URL` 与 `RATELIMIT_STORAGE_URL`
- `CORS_ORIGINS=https://真实域名`

`CORS_ORIGINS` 必须是完整 HTTPS Origin，例如 `https://analytics.example.com`，不能使用 `*`，不要包含路径。

### Nginx

在 `scripts/deployment/nginx/youtube-analytics.conf` 或 Docker Nginx 配置中替换：

- 示例 `server_name`。
- TLS 证书和私钥路径。
- 前端静态文件绝对路径。
- 上游地址；传统部署必须保持后端监听 loopback，容器部署必须保持后端仅在内部网络暴露。

检查并重新加载：

```bash
sudo nginx -t
sudo systemctl reload nginx
sudo ss -lntp
```

公网应只看到 80/443。Flask、PostgreSQL、PgBouncer 和 Redis 端口不得直接暴露到公网。

如果前面还有 CDN、WAF 或云负载均衡，也必须关闭或脱敏 `/access/*` 的访问日志，避免私有登录路径进入日志平台。

### HTTP 验收

以下示例均在未登录的新浏览器或无 Cookie 的终端执行：

```bash
curl -I https://真实域名/health
curl -I https://真实域名/
curl -I https://真实域名/login.html
curl -I https://真实域名/api/v1/channels
curl -I "https://真实域名/私有LOGIN_PATH"
```

预期结果：

- `/health` 返回 200。
- `/`、`/login.html` 和未登录业务 API 对公网表现为 404。
- 正确私有入口返回 200，并包含 `Cache-Control: no-store` 和 `X-Robots-Tag`。
- 错误私有入口返回 404。
- 连续错误登录会触发 429，并在 `logs/security.log` 留下脱敏事件。

### 验收

- [ ] `nginx -t` 成功。
- [ ] HTTPS 证书链正常，HTTP 自动跳转 HTTPS。
- [ ] HSTS、安全响应头和私有入口 no-store 已生效。
- [ ] CORS 只允许真实 HTTPS Origin。
- [ ] 公网端口扫描只发现预期端口。
- [ ] 登录、退出、会话过期、密码修改和限流均验证成功。
