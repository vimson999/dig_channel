# 新项目研发经验、纪律与标准手册

> 来源：`dig_ytb_channel` 的研发规范、生产运行手册、工作流标准、数据库规范、任务恢复纪律和历次故障复盘。
>
> 用途：新项目立项、技术方案评审、开发自检、上线验收和故障复盘。本文提炼可迁移的原则，不要求新项目复制现有项目的历史结构。

## 一、先给结论

新项目最应该继承的不是某个脚本、某个表或某个框架，而是下面这套闭环：

```text
需求边界
  → 领域模型与状态机
  → 可恢复的任务编排
  → 有边界的外部调用
  → 结构化观测与告警
  → 对账、补偿、人工接管
  → 真实流量验收
  → 故障记录反哺标准
```

本项目证明：单个功能“能跑”并不等于系统可靠。真正容易出问题的是跨进程、跨队列、跨数据库事务、跨外部平台的交接点。因此，新项目应优先把“状态、责任、恢复、证据”定义清楚，再扩展业务功能。

## 二、本项目沉淀出的核心研发经验

### 1. 先定义系统边界和事实来源

- 项目实际已经从“数据抓取”演化为内容生产链路：同步、清洗、AI 处理、素材、音频、视频、发布、监控和通知共同构成系统。
- 每个重要对象必须有唯一事实来源。业务任务表是业务状态的事实来源，Celery result 只能作为运行线索，不能作为最终业务状态。
- 在项目早期就画出四张图：领域实体图、工作流/状态图、队列与 worker 图、前端页面/API 图。
- 文档要有可信顺序，并标明哪些是现状、哪些是计划、哪些已经废弃。README、端口、API 目录和前端 API base 不一致，会直接增加排障成本。

### 2. 工作流要按状态机设计，而不是靠“跑到哪算哪”

- 每条长流程都要有稳定的 `feature`、`queue`、父任务 ID 和可查询的步骤码。
- 父任务、子任务、产物和通知之间要有显式关联；不能只靠任务名称、时间或文件名猜关系。
- `pending`、`processing`、`waiting/deferred`、`completed`、`failed`、`canceled` 的语义必须固定，前端展示状态也要有统一映射。
- 外部发布还要区分“已提交”“平台审核中”“已公开”“已验证”，不能把“接口返回成功”当作最终发布成功。
- 等待外部事件时，任务应进入 `waiting_*` 或 `deferred_*`，释放 worker 和数据库连接；不能让父任务长期占用 worker 轮询。

### 3. 幂等性是自动化系统的第一生产力

- 每个阶段都要有稳定的业务去重键，例如 `source_task_id + stage + version`，重复投递只能复用或安全更新，不能产生重复副作用。
- 只复用完整产物：文件存在、大小非零、格式可读、模板版本匹配、数据库状态为完成。半成品不能被当作成功结果。
- 重试从失败阶段继续，保留已经完成的子任务和产物；不能把一次局部失败变成全链路重跑。
- 队列投递、状态更新、通知发送要有可追踪的事件或 outbox 记录，避免“数据库已提交但消息没发出”或“消息发出但数据库没记录”。
- 子任务要记录父任务、来源任务、角色、标题、Celery ID、业务状态、步骤、进度、错误和时间。

### 4. 数据库连接和事务生命周期必须受控

所有涉及数据库和外部 I/O 的代码，统一采用三段式：

1. 短事务读取必要字段或写入前置状态，提交并释放 session。
2. 在无数据库 session 的情况下执行网络、浏览器、AI、音频、文件、Celery、Redis 或等待操作。
3. 用 ID 在新事务中重新加载，写入结果、错误或下一状态，再提交并释放。

必须遵守：

- 不跨 `commit`、`remove` 或长等待继续使用旧 ORM 对象。
- 不使用 `flush → 外部调用 → commit` 的长事务模式。
- 异常重试前先 `rollback/remove`，不能把坏事务带入下一次尝试。
- 连接池不是并发控制；并发、速率和准入要由队列、信号量、限流和状态机控制。
- 列表、轮询、watchdog 只读结构化投影，禁止每次拉取大型 JSON 或完整关系树。

### 5. 外部系统永远是不确定的

- 每次外部调用都要有连接超时、读取超时、总超时、重试上限、退避策略和最终失败状态。
- 上传类流程必须区分可重试错误和不可重试副作用；不能在未知远端状态下无限重试或随意强杀。
- 浏览器自动化要有页面/浏览器/账号/任务级的状态检查、超时和回收策略。
- 任务卡在进度百分比时，先核对时间基准、心跳、队列状态、worker 日志和外部状态，再判断是否真正卡死；数据库 UTC 与本地时区混用曾导致误判。
- “停止任务”不等于“外部副作用已经撤销”。对于已提交、审核中或可能已经生成远端资源的流程，必须先记录不确定性，再决定取消、补偿或人工接管。

### 6. 运行态和代码态是两套事实

- 代码改了不代表 worker、scheduler、watchdog 和 backend 已经加载新代码；上线验收必须核对 PID、启动时间、版本/提交号和健康状态。
- 重启要有安全顺序：先确认没有不可中断阶段，暂停调度/消费，停止 watchdog，再停止 backend、worker 和 scheduler，启动后逐个验证健康、队列和业务状态。
- “进程还在”不代表“系统可用”：要同时检查 HTTP health、Celery active/reserved/scheduled、数据库连接、业务任务心跳和关键产物。
- watchdog 只可修复明确可判定的孤儿任务，并且必须尊重人工暂停；不得用无限重启掩盖状态机或连接泄漏问题。

### 7. 监控必须回答“业务是否完成”

至少要同时观测四层：

| 层级 | 必须能回答的问题 |
| --- | --- |
| 进程 | backend、worker、scheduler、watchdog 是否存活，PID 是否为新版本？ |
| 队列 | pending/active/reserved/scheduled/retry/deferred 是否有解释？ |
| 业务 | 每个父任务和关键子任务当前状态、步骤、进度、年龄、心跳是什么？ |
| 产物 | 文件、发布记录、通知和外部可见状态是否真的完成？ |

任何自动修复都要留下审计：旧状态、旧 Celery ID、新 Celery ID、原因、执行人/程序、输入校验结果、结果和下一步。

### 8. 测试要覆盖交接点，而不是只测 happy path

- 单元测试：状态转换、去重键、重试边界、超时配置、权限和参数校验。
- 集成测试：数据库事务释放、队列投递、父子任务关联、通知、产物检查。
- 端到端测试：从输入到最终产物/发布验证，包含延迟、失败、恢复和重复投递。
- 运行冒烟：新进程启动、健康检查、最小真实任务、任务完成、产物存在、通知到达。
- 故障测试：消息不可见、worker 重启、数据库短暂断开、外部接口超时、重复回调、进程中途退出。
- 性能验收不能停在 SQL、索引或单元测试；必须经过迁移、进程替换和真实负载，观察完整业务输出。

### 9. 每个真实故障都要变成组织记忆

故障记录至少包含：症状、影响范围、时间线、状态/日志/SQL 证据、根因代码与架构、修复、验证、预防措施、复发元数据和关联记录。

同类故障第二次出现时，要做横向扫描并补共享护栏和两类入口测试；第三次出现时，应视为架构债务，停止继续复制旧模式。

## 三、新项目必须集成的研发纪律（MUST）

### 1. 仓库和路径纪律

- 源码、配置、测试、运行数据、日志、上传文件、临时文件分离。
- 资源路径从模块文件位置推导，禁止依赖 `os.getcwd()` 或 `Path.cwd()`。
- 大型二进制不进 Git；使用对象存储或受控数据目录，并记录版本和校验信息。
- 日志统一写入规定目录；日志、数据库和用户数据不能混在源码目录。
- 提交前检查密钥、cookie、token、个人数据和生成文件。

### 2. 需求和设计纪律

每个需求必须先写清：

- 不做什么，以及边界条件。
- 领域对象、唯一 ID、状态机和终态。
- 输入、输出、错误、重试、取消和恢复语义。
- 外部副作用及其“已提交/已可见”的判定方式。
- 数据保留、权限、审计和敏感信息处理。
- 监控指标、告警条件和人工接管入口。

方案评审必须回答“如果进程在每个交接点退出，会发生什么？如何恢复？”

### 3. 任务编排纪律

每个可异步流程都要登记：

```yaml
feature: stable_feature_name
queue: explicit_queue_name
business_key: deterministic_dedup_key
parent_task: business_id_and_status
steps: stable_step_codes_and_progress_ranges
children: role/source/attempt/status/output
retry: retryable_errors/max_attempts/backoff
timeout: connect/read/total/heartbeat
recovery: watchdog_or_reconciler_entry
notifications: idempotent_event_names
```

队列、API、worker、监控页和通知模板必须在同一个变更中登记，禁止只改其中一层。

### 4. 数据库和容量纪律

- 为高频列表、轮询和监控设计专用结构化投影，避免把业务大 JSON 当查询接口。
- 迁移必须同时考虑写入路径、历史数据、索引、权限、回滚和线上兼容窗口。
- 为数据库连接、外部账号、浏览器实例、CPU、磁盘和第三方限额定义预算和准入状态。
- `deferred_*` 必须能查到下一次恢复时间、原因、重试次数和负责的恢复器。
- 任何性能修复都要记录基线、代码/迁移版本、实际运行 PID、真实样本和业务完成证据。

### 5. 外部调用和资源回收纪律

- 所有外部调用有明确总超时和重试上限；默认值可配置但必须有合法范围。
- 每个浏览器、文件句柄、临时目录、数据库 session、锁和子进程都有 `finally` 清理路径。
- 回收动作要有安全判定：无远端副作用或已明确可取消时才自动回收；状态不确定时转人工。
- 不通过强制中断来“解决”一个正在发生外部副作用的任务。

### 6. 发布和部署纪律

上线顺序固定为：

1. 代码、配置和迁移评审通过。
2. 运行新迁移并验证权限、索引和兼容性。
3. 平滑替换相关进程，不假设热加载。
4. 验证新 PID/启动时间/版本号和 health。
5. 投递一条最小真实任务，观察队列、业务状态、产物和通知。
6. 验证旧任务、孤儿任务、暂停开关和回滚路径。

## 四、适合新项目直接采用的标准

### 1. 状态机不变量

| 状态 | 必须满足的条件 | 自动动作 |
| --- | --- | --- |
| `pending` | 有可追踪的队列消息、计划任务或明确 deferred 原因 | 对账发现缺失时按业务 ID 补投 |
| `processing` | 有活跃 worker 或近期心跳 | 超过阈值进入恢复判定，不直接盲目重跑 |
| `waiting_*` | 等待外部事件、审核或依赖，已释放 worker/session | 事件回调或延迟恢复唤醒 |
| `deferred_*` | 有容量/准入原因、下次检查时间和次数 | 恢复器有限次重试，超过上限告警 |
| `completed` | 业务状态、关键子任务、产物、通知均完成 | 只读归档，禁止普通重试覆盖 |
| `failed` | 有结构化错误、失败阶段和可重试标记 | 只从失败阶段重试 |
| `canceled` | 取消原因、操作者和外部副作用说明完整 | 不再自动重投，必要时人工补偿 |
| `submitted/reviewing/visible` | 外部平台状态有来源和最后验证时间 | 按验证结果推进，不把提交响应当公开 |

### 2. 统一恢复原则

- 先对账，再修复；先读证据，再改状态。
- 以业务 ID 重试/补投，不能只凭 Celery ID 或日志文本。
- 修复前校验输入文件、账号凭证、父子引用和产物完整性。
- 修复后验证新消息、业务状态、关键子任务、最终产物和通知。
- 重复失败、状态矛盾、权限不足、远端副作用不确定时停止自动修复并升级人工。

### 3. 统一可观测字段

所有日志、事件、通知和审计至少带：

`project_id`、`workflow_id`、`business_task_id`、`parent_task_id`、`child_task_id`、`feature`、`queue`、`step`、`attempt`、`code_version`、`process_id`、`created_at`、`updated_at`、`error_code`。

时间统一存 UTC，展示时明确时区；不要用“看起来两小时没动”替代心跳和时间线证据。

### 4. 前端与 API 标准

- API base、版本和错误格式统一配置，不在页面里散落硬编码地址。
- API 目录只保留一个主入口；遗留入口必须有迁移计划和注册说明。
- 列表接口返回结构化摘要和分页，不返回大型结果 JSON。
- 状态胶囊、步骤、进度、错误、复制、取消、重试、预览和下载动作统一。
- 用户看到的状态必须能回溯到后端状态机和审计事件。

### 5. 安全标准

- 凭证进入加密存储，业务代码只拿到最小必要权限。
- 日志、错误、通知和导出物脱敏；cookie/token 不进入 Git、截图或普通日志。
- 外部回调校验签名、来源、幂等键和时间窗口。
- 所有管理动作记录操作者、原因和影响对象。

## 五、哪些经验不要原样复制

下面是本项目中值得在新项目中主动改进的历史包袱：

1. **文档和实际运行配置不一致**：新项目要把端口、启动方式、队列、API 路由、前端入口作为可生成或可校验的单一配置。
2. **API 目录分裂**：新项目只保留一个明确的 API 入口；确需兼容时用版本化迁移，不再新增平行目录。
3. **用一个大 JSON 承担所有任务信息**：将高频字段拆成列，将完整日志/结果放到独立表或对象存储。
4. **靠多个独立开关连接阶段**：跨阶段交接必须有持久化事件、outbox 或对账器，不能依赖“另一个任务稍后会发现”。
5. **父任务长期等待子任务**：改为事件驱动、延迟重试或状态机唤醒，worker 只做有限工作。
6. **只对 allowlist 任务做恢复**：恢复器要面向状态不变量和业务 ID，新增 workflow 不应因为漏注册而永久失联。
7. **默认允许无限重试**：所有上传、浏览器和网络调用必须有总超时、最大尝试数和人工接管。
8. **把 worker 存活当成服务健康**：同时检查 backend health、队列、业务心跳、数据库和真实输出。
9. **把代码更新当成部署完成**：必须替换进程并做真实任务验收。
10. **只看百分比判断卡死**：使用统一时区、心跳、最后状态变更时间和阶段超时模型。

建议在仓库初始化时一次性建立：

```text

docs/PROJECT_CONTEXT_MAP.md       # 系统边界、事实来源、关键路径
docs/ARCHITECTURE.md              # 组件、数据流、状态机、容量预算
docs/WORKFLOW_STANDARD.md         # 任务/队列/步骤/恢复/通知契约
docs/API_ROUTE_MAP.md             # 路由、版本、认证、错误格式
docs/QUEUE_MAP.md                 # 队列、消费者、并发、超时、重试
docs/RUNBOOK.md                   # 启停、健康检查、应急恢复、回滚
docs/adr/                         # 关键设计决策和放弃方案
docs/bugs/                        # 一事一档的故障记录
docs/bugs/recurrence-registry.json
scripts/dev/                      # 可重复、可审计的启动/停止/检查脚本
.env.example                      # 变量说明、默认安全值、敏感项提示
```

每个新功能合入前，用下面清单自检：

- [ ] 需求边界、状态机、唯一业务键已写明。
- [ ] 已搜索并评估成熟实现；不复用时记录原因和风险。
- [ ] API、任务、队列、数据库、前端、通知和监控已成套登记。
- [ ] 重复投递、进程退出、worker 重启、外部超时、取消和恢复已设计。
- [ ] 数据库操作没有跨外部 I/O 的长事务，所有异常路径会 rollback/remove。
- [ ] 关键字段有结构化投影和索引，列表/轮询不会加载大 JSON。
- [ ] 凭证、权限、日志脱敏、回调签名和审计已覆盖。
- [ ] 单元、集成、端到端、故障和启动冒烟测试已通过。
- [ ] 迁移已应用，新进程已替换，真实任务已完成并验证产物/通知。
- [ ] 文档、runbook、监控面板和回滚方式已同步更新。

## 七、建议的新项目落地顺序

### P0：先建立可靠底座

1. 统一项目结构、配置、日志、时间和 ID。
2. 定义核心实体和状态机不变量。
3. 建立任务/队列/父子/事件/outbox/审计模型。
4. 落地数据库三段式 session 纪律、容量准入和结构化投影。
5. 实现统一超时、重试、取消、恢复和对账服务。
6. 建立 health、业务心跳、队列视图、关键产物校验和告警。

### P1：再扩展业务能力

1. 接入外部平台时优先实现“提交—查询—验证—补偿”闭环。
2. 把成熟的渲染、浏览器、AI 和通知能力封装成可复用适配器。
3. 建立端到端和故障注入测试矩阵。
4. 建立性能基线、容量预算、保留策略和定期演练。

### P2：持续降低复杂度

1. 用生成的路由图、队列图、页面图替代手工过期文档。
2. 合并重复 API/模块，明确边界和所有权。
3. 将运行指标、任务事件和故障记录接入统一查询面板。
4. 每 7 天或每 5 个真实故障做一次复盘；重复故障立即升级架构治理。

## 八、最终判断标准

一个功能只有同时满足以下条件，才算“完成”：

> 代码完成 + 测试通过 + 迁移生效 + 新进程已加载 + 真实任务成功 + 关键产物可验证 + 通知/审计完整 + 失败可恢复。

如果只能证明“接口返回 200”“Celery 已入队”“进程还活着”或“单测通过”，只能称为局部完成，不能称为生产完成。

新项目的最高优先级不是让所有流程都自动化，而是让每个流程在失败、重启、重复投递和外部不确定的情况下，仍然能被解释、被恢复、被审计。
