# 2026-07-14 飞书 Docs 首页被误判为目标文档正文

## 现象

知识星球 item `82255482825284252` 指向飞书 Wiki 文档，但“抓取”得到的标题是 `Docs`，正文是“模板推荐、考勤管理、CRM、明星企业案例”等飞书首页内容，与原帖完全无关。

## 根因

飞书在 Cookie 失效、账号无权访问或 Cookie 不适用于当前域名时，仍可能对 Wiki URL 返回 HTTP 200。原抓取器只校验 HTTP 状态码，再对整页 HTML 做通用文本抽取，因此把飞书 Docs 首页壳层当成了成功正文，并把该凭据误标为可用。

## 修复

- 在写入数据库前校验飞书响应内容。
- 目标 Wiki 成功解析后应显示文档自身标题；只要响应标题仍为飞书应用壳层的 `Docs`，无论首页推荐内容如何变化，都明确报错并拒绝保存。
- 对标题异常但同时命中多项首页壳层特征的响应也继续拒绝，作为第二道防线。
- 空正文同样在抓取层报错，不再形成“成功但无内容”的记录。
- 增加单元测试，覆盖 HTTP 200 + Docs 模板首页的假成功场景，并保留正常正文通过场景。

## 现场处理

- 清理 item `82255482825284252` 已误存的 Docs 首页正文、标题、哈希及抓取元数据。
- 将文档恢复为 `failed`，页面显示明确的凭据/权限错误，更新飞书凭据后可直接重试。

第一次修复仅组合判断 `Docs` 标题与当时的“模板推荐”特征。飞书随后返回另一版“入门推荐/自动化流程/可视化仪表盘”首页，仍以 `Docs` 为标题，导致关键词规则漏判。现已改为以 `Docs` 壳层标题作为稳定拒绝条件，正文关键词只作辅助判断。

## 复发预防

外部页面抓取不能以 HTTP 200 作为业务成功条件。必须同时校验最终页面类型、正文特征和登录/应用壳层特征；只有通过内容真实性校验后才能保存正文并标记凭据成功。
