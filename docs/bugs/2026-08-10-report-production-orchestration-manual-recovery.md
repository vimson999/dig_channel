## 现象与人工成本

同一批三份 PDF 使用“完整视频 + PDF 首屏横版 + 方案三竖版”时，前两份父任务停在
`pub_waiting`，第三份因并发门禁延后；Publisher 已完成后父任务仍要等待下一次 60 秒轮询。
个别父任务虽然在后置视频环节失败，但文案和 WAV 已有效，视觉入口却曾按父任务失败状态拒绝复用。

人工操作需要跨研报详情、视觉工作流、Publisher 和任务数据库判断真实进度，再决定续跑哪个节点。
批量处理时既容易误判“卡死”，也容易重复创建 Publisher 或重做已经有效的文案、音频和视觉资产。

## 根因

1. 研报任务内部步骤叫 `publisher_video_*`，持久化时 `_current_step_code()` 压缩为 `pub_*`；
   runtime guard 只排除了未压缩前缀，导致 `pub_waiting/pub_v_synthesis` 被计入运行容量。
2. 父任务只靠 60 秒延迟消息轮询 Publisher；子任务终态没有幂等事件唤醒。
3. 父任务 `failed` 被错误等同于文案/WAV 不可用，任务状态与产物有效性耦合。
4. 完成判断主要依赖路径存在，没有统一验证文件非空、音视频流和时长一致性。
5. 工作台缺少等待对象、容量保护、质量门禁和缺失产物摘要，迫使运营人员查原始 JSON 或数据库。

## 实际方案

- runtime guard 同时识别内部前缀和持久化压缩前缀；被动等待父任务不占执行容量。
- Publisher 成功或失败后，以等待 token 和旧 broker ID 做 compare-and-set，预分配新的即时续跑 ID；
  重复终态事件只接受一次，旧延迟消息由父任务入口判为 stale，发布失败则恢复原兜底消息。
- 方案三提交阶段自动建立视觉依赖；后置失败父任务只要文案、WAV 和身份匹配仍可复用。
- 共享完成契约验证全部所选横竖版：文件存在且非空、FFprobe 可读、包含音视频流、时长与最终 WAV
  在允许误差内。任一输出失败时记录 `missing/reason`，不得写成完成。
- 详情 API 输出七阶段、等待子任务、容量保护、下次重试和完成契约摘要；前端区分已复用、等待、
  需要处理和未启用。发布阶段继续只受既有显式开关控制。

## 确定性验证

- 三个 `pub_waiting` 父任务在容量上限 2 时 `active_count == 0`，第三任务允许启动。
- 三个 Publisher 分别收到一次即时父任务续跑；重复终态通知均返回 `already_woken`。
- 父任务消费终态后清除 `waiting_child`，每个父任务仍只有一个 Publisher。
- 横版与方案三竖版均通过共享完成契约，原 WAV、文案和视觉路径保持不变。
- B站投递结构表保持 0 条；测试没有触发内容生产、平台上传或外部网络调用。

3. 每个父任务最多一个有效 Publisher，不出现方案三失败风暴；
4. 三份任务均有横版和方案三 MP4，完成契约为 ready；

## 复发预防

- 所有压缩状态码必须和运行时守卫建立双向合同测试。
- 父子编排采用事件优先、轮询兜底，终态回调必须带 compare-and-set 幂等键。
- 复用判断以产物身份与质量门禁为准，不以父任务最终状态一票否决。
- 新增视频变体必须先加入共享完成契约和七阶段状态映射。
- 自动发布边界必须在集成测试中持续断言为显式 opt-in。
