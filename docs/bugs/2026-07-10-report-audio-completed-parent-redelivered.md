# 2026-07-10 研报音频已完成父任务被延迟消息再次执行

## 基本信息

- 状态：已修复
- 严重级别：高
- 影响模块：`report_pdf_audio_workflow` / 延迟续跑 / Celery 幂等收口
- 首次发现：2026-07-10，任务 `c8cd785d-966f-4e25-a716-4f052b009dee` 现场续跑验证
- 修复提交：待提交

## 现象

任务在 `12:48:48` 已完成到 `done / 100%`，但此前排队的延迟续跑消息随后被 worker 收到，父任务又从 `completed` 被改回 `processing`，重复执行结构化复用、豆包复用和关键帧生成。

## 影响

- 页面上的已完成状态会短暂倒退为运行中。
- 重复读取大结果、重复生成关键帧，造成数据库和 CPU 浪费。
- 如果后续阶段包含非幂等外部动作，可能产生重复提交风险。

## 根因

父任务采用延迟消息实现状态机续跑，但 `_process_job()` 入口只拦截 `canceled`，没有把 `completed` 作为终态幂等门槛。Celery 的正常重复投递或较早排入的倒计时消息因此可以重新执行已完成任务。

## 解决思路

在任何业务状态修改之前检查终态。`completed` 必须直接成功返回；重复消息只能被确认消费，不能重新进入工作流。

## 实际方案

- `_process_job()` 加入 `completed` 硬门槛并记录幂等跳过日志。
- 保留 `canceled` 直接退出行为。
- 新增数据库回归测试，确认重复投递不会发送通知、不会修改状态、步骤和进度。

## 验证

- 已完成父任务重复投递单元测试通过。
- 现场任务最终稳定收口后，延迟消息应只打印 skip 日志并返回成功。

## 复发预防

- 所有可重试、可延迟、acks-late 的父编排入口必须显式处理终态幂等。
- 完成状态写回后不得存在能够将其无条件改回 processing 的代码路径。
- 工作流测试必须覆盖“完成后重复投递”场景。

## 后续事项

- 静态审计其他父编排入口是否缺少 completed/canceled 终态门槛。
