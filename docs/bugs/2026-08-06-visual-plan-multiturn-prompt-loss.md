## 现象

任务 `3b5e2b81-1979-4d91-84ea-5427bf77e7cd` 的基础文案已完成，但标题与正文分镜阶段失败，
页面显示“DS 改写或翻译了 Gem 提示词，已拒绝保存”。页面同时错误显示“基础文案完成后可生成分镜”，
没有说明原始 Gem 回复仍可复用。

## 影响

分镜没有写入结构化输出，后续图片、语音、时间轴和视频阶段全部无法启动。人工点击“复用 Gem 原文继续梳理”
仍会失败，并重复消耗 DS 整理请求。

## 根因

Gem 使用两轮回复：第一轮包含标题和正文分镜 1--10，第二轮从分镜 11 开始继续。浏览器 worker 虽然在
checkpoint 中维护了合并文本，但最终结果错误地把 `turns[-1]` 当作 `response_text`，导致标题和前十个分镜在
normalizer 入口丢失。

同时，浏览器完成判断只验证 `【文案原句】` 是否覆盖全文，没有验证每个文案片段都存在
`【AI 提示词】`。本次第二轮末尾 11 个片段缺少提示词，却带有完成标记，流程因此提前结束；DS 看到缺失的
Gem 原始提示词后被错误归因成“DS 改写”。

## 实际方案

- `GeminiBrowserWorker.generate()` 在没有普通 follow-up 时返回所有分镜轮次的合并文本；只有显式普通 follow-up
  才切换为该 follow-up 的最终回复。
- 分镜浏览器完成判定增加逐片段提示词完整性检查；缺字段时继续追问，并要求补齐旧轮次的缺失字段。
- 续跑 checkpoint 按初始轮和分镜 continuation 顺序重建文本，不再只读取历史的最后一轮。
- DS 整理后按 Gem 标签顺序恢复原始提示词；标签序列不完整时 fail-closed，并报告“需要/实际”条数和重新请求建议，
  不生成或猜测缺失提示词。
- 详情页失败态显示可复用原始 Gem 和两种恢复路径，不再误显示“基础文案完成后可生成分镜”。

## 验证

- Python 编译和 `git diff --check` 通过。
- 回放当前 Gem 存档确认：合并后有 41 个文案片段、30 个提示词，完成判定为 false；续跑整理会报告需要 41 条、实际 30 条。

## 复发预防

1. 多轮 AI 结果必须以合并文本作为最终输入，checkpoint 和最终返回使用同一权威内容。
2. 完成判定必须同时验证源文案覆盖和每个结构化片段的必填字段，完成标记不能绕过字段校验。
3. DS 只能修复结构和原文边界，Gem 的视觉提示词逐字保留；缺失字段必须明确失败并引导重新请求。
4. 每次同类失败都补充多轮、缺字段、续跑和页面状态回归测试，避免只修单个任务数据。
