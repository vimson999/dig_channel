# 2026-07-28 PDF 证据契约被旧前端覆盖且旧格式无法验证

## 基本信息

- 状态：已修复并完成两份真实 PDF 横竖成片验收
- 严重级别：P1
- 影响模块：研报音频 / Gemini 浏览器 / PDF 证据映射 / 视觉分镜
- 首次发现：2026-07-28
- 修复提交：待提交
- 根因分类：跨层提示词契约 / 外部模型响应兼容
- 复发键：REPORT-PDF-EVIDENCE-CONTRACT
- 是否复发：首次
- 关联记录：无
- 防线层级：shared_guardrail / contract_test / observability

## 现象

新任务完成 Gemini、文案和 TTS 后，证据面板显示 unavailable，错误为“Gemini 返回中没有可识别的证据候选”。实际保存的 Gemini 原文尾部存在完整 `evidence_map` JSON。

## 影响

PDF 页、原文和截图指令没有进入本地复核与人工编辑，分镜只能降级为普通生成画面。若只按 unavailable 理解，会误判为模型没有返回证据。

## 根因

页面硬编码了旧版自审提示词，并以非空任务级值覆盖服务端已升级的 `PDF_EVIDENCE_V1_JSON` 契约。Gem v6 仍按自身旧格式返回 `script_paragraph_index/pdf_pages/source_excerpt`，而本地解析器只识别新 claims 字段。服务端缺少不可绕过的契约合并边界。

## 解决思路

把证据输出契约提升为服务端所有入口都必须追加的固定契约，同时保留前端可编辑的业务自审文本。对已存在的 Gem v6 格式只做候选兼容，仍必须通过最终 TTS 文案定位和本地 PDF 页原文匹配才能成为 verified 证据。

## 实际方案

- 新增幂等的服务端证据契约合并函数，API 入库和 Celery 执行边界均调用。
- 更新页面默认值和缓存版本，但不依赖前端正确性保障后端契约。
- 解析器 v2 识别 Gem v6 `evidence_map`，跳过 `needs_pdf_evidence=false`。
- 旧格式段落索引不直接作为验证事实；结合截图指令、PDF 原文和最终文案单元做本地映射评分。
- 页码越界、PDF 原文不匹配或文案映射不足仍保持 partial/unverified，不进入证据画面。
- 全局 CORS 方法白名单补齐 `PATCH`，人工换页、裁剪、启停证据画面可从真实页面保存。
- 分镜链接支持“短分镜子句完整包含于长证据主张”，并对过短通用片段保留阈值保护。

## 验证

- 单元测试覆盖旧提示覆盖、幂等合并、v6 旧格式、无证据、错误页码和 TTS 污染拒绝。
- 定向回归覆盖提示词契约、解析、污染门禁、编辑接口和分镜链接。
- 样本1保存原文解析出 8 个旧格式候选；严格复核后仅 3 个 verified，其余保持 partial/unverified。
- 样本2真实 Gem 三段回复完整保存，11 个候选中 2 个 verified；人工编辑状态、证据截图和分镜链接均已在页面与数据库验证。

## 复发预防

- 证据契约由服务端拥有，旧前端、缓存和任务级 prompt 都不能删除。
- 解析器版本写入证据输出，升级后不会误复用旧 unavailable 缓存。
- 新旧响应格式都必须经过同一 PDF 页文本与最终脚本复核。

## 后续事项
