# 2026-06-23 研报音频编排 detached ORM 对象

## 基本信息

- 状态：已修复
- 严重级别：高
- 影响模块：`report_pdf_audio_workflow`
- 首次发现：研报音频编排任务在子任务完成后进入失败状态
- 修复提交：已随本地修复提交过

## 现象

研报音频编排父任务在 Gemini、豆包朗读等子任务完成后，后续汇总阶段报错：

```text
Instance <PublicationTask ...> is not bound to a Session; attribute refresh operation cannot proceed
```

页面表现为父编排失败，但部分子任务已经完成，进度停在后段。用户会看到“视频合成未执行”或父任务直接失败。

## 影响

- 父编排可能在子任务实际成功后失败。
- 已生成的音频、结构化结果、子任务状态可能无法被正确汇总到父任务。
- 用户需要人工判断哪些产物可复用，增加误操作和重复执行风险。
- 如果继续沿用旧 ORM 对象，类似问题会在长等待、释放连接、重试恢复等路径反复出现。

## 根因

父编排为了避免长时间占用数据库连接，会在等待子任务期间释放 SQLAlchemy session。释放 session 后，代码后续仍持有旧的 `PublicationTask` ORM 对象，并继续读取其 `status`、`result` 等属性。

SQLAlchemy 在访问已过期或未加载属性时需要回到 session 刷新对象；对象已经 detached，就触发 detached session 错误。

架构层根因是：长耗时编排中把“任务身份”和“ORM 实例生命周期”混在了一起。ORM 对象不适合作为跨等待阶段的状态载体。

## 解决思路

等待子任务时只保留稳定的任务 ID，不保留旧 ORM 对象。每次需要判断状态或生成摘要时，用短生命周期查询重新从数据库加载最新记录，读完后释放连接。

这个方案解决的是“不能拿 detached 对象继续读”的直接 bug，同时也符合连接池压力下的运行策略：等待期间不长期占用数据库连接。

更进一步的生产级方向是把长等待改成状态机恢复模式：父编排投递子任务后进入 `waiting_*` 状态，由子任务完成回调、定时 reconciler 或延迟任务唤醒下一阶段，父 worker 不长期占坑。

## 实际方案

- 子任务创建后保存 `child_task_id`。
- 等待循环和汇总逻辑通过 ID 重新查询 `PublicationTask`。
- 生成父任务摘要和最终结果时重新加载子任务结果。
- 避免在 session 释放后继续访问旧 ORM 实例。

## 验证

- 复查失败任务，确认错误来自 detached ORM 对象访问。
- 跑相关单元测试，覆盖 report audio 子任务等待、摘要和续跑相关逻辑。
- 复测失败任务续跑路径，确认父任务可以完成并正确汇总子任务产物。

## 复发预防

- 编排代码中跨等待阶段只传任务 ID，不传 ORM 对象。
- 长耗时等待必须允许释放 DB session。
- 新增或修改编排等待逻辑时，必须检查是否有 detached ORM 访问风险。
- 后续应逐步把豆包多分段等待和 publisher 视频合成等待改成状态机恢复，减少父 worker 长时间等待。

## 后续事项

- 在编排标准中补充“跨等待阶段禁止持有 ORM 实例”的明确约束。
