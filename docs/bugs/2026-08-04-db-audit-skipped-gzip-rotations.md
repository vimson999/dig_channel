# DB 巡检遗漏当日 gzip 轮转日志

## 基本信息

- 状态：已修复并用完整窗口重新巡检
- 严重级别：P1
- 影响模块：数据库巡检 / 页面与 API 端到端统计 / PgBouncer 事件统计
- 首次发现：2026-08-04
- 修复提交：当前工作区
- 根因分类：可观测性覆盖不完整
- 复发键：`REGRESSION-ACCEPTANCE-INTEGRITY`
- 是否复发：首次
- 关联记录：`2026-07-18-regression-suite-false-green-and-live-side-effects.md`
- 防线层级：observability / contract_test

## 现象

每日巡检器只扫描活动日志和普通文本轮转，明确跳过 `.gz`。2026-08-04 02:00 日志维护把当日约 7.4MB `backend.log` 和 5.9MB `pgbouncer.log` 压缩轮转后，原统计会漏掉窗口前约 20 小时的请求和连接池事件。

## 影响

- 页面/API 请求量、P50/P95、失败率和 request id 到 SQL 的关联会被低估。
- PgBouncer 的 query/connect timeout 以及本轮 HBA 拒绝会被漏报。
- 仅看活动文件可能把“没有被捕获”错误表述为“没有问题”。

## 根因

分析器早期为避免扫描历史大文件，只接纳普通文本轮转；选择条件没有利用轮转文件 mtime 与巡检起点判断是否可能和窗口相交。

## 解决思路

统一普通文本和 gzip 的容错文本读取；活动文件始终扫描，轮转文件仅在 mtime 不早于窗口起点时扫描，以补齐窗口同时避免每天重读全部历史归档。

## 实际方案

- 新增 `open_log()`，统一读取文本与 gzip。
- 事件日志和 Celery 日志发现纳入可能与窗口重叠的 `.gz`。
- PgBouncer 统计同时覆盖活动文件与当日 gzip 轮转。
- 补充 HBA/server login 分类，并输出应用慢 SQL 累计耗时。
- 低频高延迟桶扩大到不超过 5 个样本，避免 4-5 次的严重长尾被遗漏。

## 验证

- 分析器单测 `12 passed`。
- 同一窗口重跑得到 3,460 个完整请求、126 个端点；旧逻辑在 02:00 轮转后会丢失窗口主体。
- PgBouncer 新统计捕获 1,054 次 `server_login_failed/hba_rejected`，并保留 connect/query timeout 与 wait/query 分位数。

## 复发预防

- 所有基于滚动日志的巡检必须同时覆盖活动、文本轮转和窗口相交的压缩轮转。
- 每次日志维护策略变化后必须用跨轮转边界的测试样本验证。
- “0 次事件”必须同时报告扫描文件与时间覆盖，不能脱离观测边界解释为健康。

## 后续事项

- 下一轮继续核对 gzip 与活动文件去重后端点数，防止共享 handler 造成重复统计。
