## 为什么看起来每天都在修

1. **把局部路径当成能力。** 一个函数改成轻量查询后，另一个 API、worker 或 watchdog 仍有复制实现。
2. **把源码检查当成 SQL 合同。** 旧测试确认出现候选查询，却没有禁止候选循环后的 N+1 或 commit 后隐式刷新。
3. **只修读取端。** JSON 仍是新数据唯一事实源，下一条查询自然又只能回到 JSON。
4. **发布阶段被省略。** 代码、迁移、权限、历史回填、进程替换和真实负载没有独立状态。
5. **旧进程污染结论。** 日志来自部署边界前 PID 时，既不能证明新代码失败，也不能证明修复成功。
6. **锁等待被误判为索引问题。** 在线 DDL 的等待锁能让所有后续 SELECT 排队，查询本身再快也无济于事。
7. **验收窗口太短。** 只观察主任务或空闲期，漏掉完成后的清洗、资产扫描、通知和 watchdog 消费者。
8. **测试 SQL 混入生产日志。** 未标进程角色和方言时，人工统计会把 pytest/SQLite 样本算成生产复发。

## 根治方案

### 1. 入库

- B站上传在创建任务的同一事务写 `publication_task_bilibili_uploads`。
- ZSXQ 下载在附件成功事务写 `zsxq_sync_run_downloads`。
- 内容清洗终态同时写五个有界投影列；bulk UPDATE 和 ORM 写入都覆盖。

### 2. 表结构

- `params/result` 保留完整请求、审计和冷详情，不再承担列表、关联、状态机或批次集合索引。
- 稳定实体使用一对一扩展表；可增长集合使用关系表；高频状态使用普通列。

### 3. 历史迁移

- 只在一次显式事务中完成建表、补列、回填、权限、索引清理和验证。
- 脚本检测任何 `cappa_rw` 在线连接即失败，防止 DDL 锁队列。
- 不能证明完整的 21 个旧 ZSXQ 批次保留明确 legacy 标记，不伪造数据。

### 4. 查询与状态写入

- 两个 B站 API 共用一个服务；历史固定一次 JOIN；创建和 watchdog 使用 commit 前 DTO。
- TTS 终态按结构化列收口；轮询、列表和 watchdog 禁止读取任务 JSON。
- worker 终态写 JSON 的同时维护结构化结果，不牺牲标题、账号、产物或错误信息。

### 5. 可执行门禁

- 启动前检查表、列、权限、索引、历史回填和重复索引；不完整就拒绝启动所有服务。
- 实际 SQL 测试锁定查询次数和列集，覆盖完整 API/service/watchdog 调用，不再只扫描源码。
- 日志记录 PID、启动时间、角色、进程和方言；分析器默认排除测试 SQL。
- 复发簇在 registry 中记录 `acceptance_stage` 和 `blocking_records`，回顾脚本校验，不允许文字口径漂移。
