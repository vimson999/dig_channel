# 重启安全门无条件切换公网数据库导致无法验收

## 基本信息

- 状态：代码与双分支测试已修复，待本次真实安全重启验收
- 严重级别：高
- 影响模块：完整重启 / 活动任务门禁 / schema 门禁 / PostgreSQL / 本地 PgBouncer
- 首次发现：2026-07-21 15:05 部署第二轮 SQL 修复时
- 修复提交：待提交
- 根因分类：控制通道选择错误、可用性探测缺失、部署验收阻断
- 复发键：`RUNTIME-TOPOLOGY-RELOAD`
- 是否复发：是；属于重启控制面与运行时拓扑复发簇
- 防线层级：fail_closed_guard / connection_fallback / branch_test / live_restart

## 现象

- 本地 PgBouncer 正常监听 `127.0.0.1:6432`，业务查询正常。
- `check-restart-safety.py` 仍无条件把 `DATABASE_URL` 覆盖为公网 `DIRECT_DATABASE_URL`。
- `check-runtime-schema.py` 也以相同顺序优先公网直连，完整重启的第 0 步同样可能被阻断。
- 公网 5432 超时后，安全门无法判断活动任务并拒绝重启；不能用强制参数绕过，否则可能中断业务任务。

## 根因

1. 旧实现只考虑“重启过程中本地代理可能已经停止”，没有核对当前重启脚本其实不会停止 PgBouncer。
2. 通道选择没有可达性探测，配置了 direct URL 就覆盖工作正常的本地 URL。
3. 单测只覆盖 direct URL 被选择，没有覆盖本地代理存活时应继续使用本地通道，测试形成单分支假绿。

## 实际方案

- 安全门先解析当前 `DATABASE_URL`；仅当它是本地地址且 TCP 端口实际可达时保留该通道。
- schema 门禁使用同一选择规则，避免两道门对数据库控制通道作出相反判断。
- 本地代理不可达时再切换 `DIRECT_DATABASE_URL`，保留代理停机场景的控制能力。
- 两条通道最终都无法连接时继续 fail-closed，绝不把“无法检查”当成“没有任务”。
- 两个门禁均新增“本地可达保留代理”和“本地不可达切直连”互斥分支测试。

## 验证

- 重启门与 ZSXQ 定向回归：`26 passed`。
- 修复后现场门禁成功通过本地 PgBouncer 查询，并正确拦截 1 个处于 `synthesis` 的 publisher 任务，证明不是假放行。
- 待完成：任务自然结束后执行完整重启，确认冻结前后两次门禁、进程拓扑和新 PID 均通过。

## 复发预防

1. 控制面存在主备通道时，必须先做有界可达性探测，再按明确优先级选择。
2. fail-closed 只负责拒绝未知状态，不能替代通道高可用；拒绝后必须修复可观测的连接选择原因。
3. fallback 测试必须成对覆盖主通道可用与不可用，禁止只测降级分支。
4. 完整重启仍需冻结前后两次查询活动任务，任何连接失败或真实活动任务都不得停止 worker。
