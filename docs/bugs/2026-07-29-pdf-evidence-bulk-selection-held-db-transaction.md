## 现象

用户点击“全部作为证据画面”后等待约一分钟，页面提示“批量设置失败：HTTP 500”。

## 影响

- 批量人工确认不可用，用户只能逐条操作。
- 长事务占用连接并阻塞同一证据输出的后续查询。
- 按钮文案让用户误以为全部勾选的截图一定进入最终成片，但当时的实现只是把它们放入分镜匹配候选集合。

## 根因

证据画面开关在数据库事务尚未结束时同步渲染 PDF 截图。截图生成属于文件和 PDF 渲染 I/O，数据库连接因此持续占用；真实请求中相关查询等待约 60 秒后触发 PostgreSQL `OperationalError`，接口返回 500。

同时，人工确认与机器验证没有独立状态，部分或未验证主张即使保存也会被重新取消“作为证据画面”。

## 解决思路

- 将人工选择状态写入与截图生成解耦。
- 批量操作只做短事务状态更新；截图在页面预览或视觉资产真正使用时按需生成。
- 用独立 `manual_verified` 状态表达人工确认，不伪装为机器验证。
- 明确区分“进入证据候选池”和“保证进入最终成片”。

## 实际方案

- 批量加入/取消一次更新所有证据主张及总开关，不再在请求事务中渲染截图。
- 单条保存也不在写事务内预生成截图。
- 分镜链接不再依赖已经存在的截图文件；视觉资产任务按需渲染。
- 前端按钮改为“全部加入证据候选池”，并说明每个分镜最多使用一张，候选图不保证全部进入成片。
- 增加人工确认、批量加入/取消和延迟截图回归测试。

## 验证

- 25 个证据服务和前端契约测试通过，5 个子测试通过。
- 前端 JavaScript 语法检查通过。
- 后端完成重启且健康检查通过。
- 真实任务 `94d2afa4-6e45-4295-bd3e-2d74f23c0621` 的 7 条主张在 1.073 秒内全部加入候选池；6 条标记为人工确认，1 条保持机器验证，总开关开启。

## 复发预防

- 数据库写事务内禁止 PDF 渲染、图片生成、浏览器操作和其他文件/远程 I/O。
- 批量 UI 动作必须有真实数据库负载验收，不能只用内存 SQLite 验证。
- 人工确认状态必须与机器验证状态分离。
- UI 不得把“候选”“匹配使用”和“强制覆盖”混成同一个产品承诺。

## 后续事项

如果产品要求“所有人工选中的证据截图至少在成片出现一次”，需新增覆盖编排层；当前策略仍是按分镜相关度选择候选证据。
