## 现象

真实任务 `27679563-79c1-4dba-a340-753faa1bbef8` 同时出现三类用户可见问题：

1. 请求中已选择 `scheme3`，详情页却没有方案三关键帧可确认。
2. 标题评审保留了两行标题，但横屏图片在渲染前把换行压平，并把“摩根士丹利”改成“大摩”，导致评审文本、编辑框和图片不一致。
3. 横屏与竖屏评审最终选中了同一个候选，违背两个版式应采用不同角度的业务要求。

## 影响

- 用户无法在生成完整竖屏视频前确认方案三模板。
- 图片文案不再忠实反映独立评审结果，人工核对失去意义。
- 横竖两个输出缺少内容差异，降低移动端封面的信息效率。
- 已完成任务看似成功，但关键视觉产物不完整，属于产物合同的假绿。

## 根因

### 代码层

1. 前端把“竖屏启用”和“选择竖屏方案”作为两个独立字段提交；用户选中方案三但没有额外勾选竖屏开关时，请求形成：

   ```text
   vertical_enabled=false
   vertical_video_schemes=["scheme3"]
   ```

   worker 仅检查前者，因此跳过全部竖屏关键帧。

2. `_publisher_cover_title_with_institution` 在渲染前调用单行压缩，把标题中的显式换行删除，再把投行全称替换成内部简称。
3. 标题选择器分别取横屏、竖屏最高分，但没有“标题不得相同”的选择后不变量。
4. `video_bg` 模板仍使用无行数上限的 `wrapText`，长标题即使数据中只有两行，也可能在 9:16 画布中变成三行。
5. API 与详情页各自实现了一套机构前缀归一化，人工重绘入口仍可能再次把全称缩写。

### 架构层

方案选择、标题评审、封面编辑、媒体渲染和详情页展示之间缺少一个统一的视觉资产合同。系统只验证“字段存在”，没有验证：

- 显式选择方案二/三是否必然产生对应关键帧；
- 评审标题是否原样进入编辑框和图片；
- 横竖标题是否满足差异化要求；
- 模板最终像素结果是否遵守两行上限。

## 解决思路

- 把方案二/三视为明确的竖屏意图，同时保留方案一默认勾选但不自动开启竖屏的兼容行为。
- 评审标题作为权威文本；渲染阶段只在标题完全没有机构时补前缀，不改写已有机构名和显式换行。
- 当横竖首选相同时，从通过原题基准分的候选中选择竖屏最高分的不同标题；没有合格替代时仍保留稳健基准，避免为了不同而降低事实质量。
- `video_bg` 使用带字号自适应与行数上限的统一文字绘制器。
- 对已评审的缓存任务执行确定性合同归一化，不重复调用 DeepSeek。

## 实际方案

- 提交页在显式选择 `scheme2` 或 `scheme3` 时自动提交 `vertical_video_enabled=1`。
- worker 对历史矛盾请求增加兼容防线：显式方案列表含二/三时仍生成竖屏关键帧。
- 标题选择器增加横竖去重与合格候选回退。
- 标题渲染、API 重绘和详情页编辑框共同保留投行全称及手工换行。
- 方案三标题与副标题改用 `drawFittedWrappedText`，分别限制为两行和一行。
- 更新前端资源版本，避免浏览器继续使用旧脚本缓存。
- 对真实任务重选标题并重新生成横屏、B站和方案三关键帧。
