# 分镜多轮 Gem 被固定总时限截断且丢失已完成回复

## 基本信息

- 状态：已修复并完成新 worker、真实长任务和 checkpoint 续跑验收
- 严重级别：高
- 影响模块：火柴人视觉视频 / 标题与正文分镜 / Gemini 浏览器自动化
- 首次发现：2026-07-27
- 修复提交：待提交
- 根因分类：外部浏览器长任务超时预算与中间产物续跑
- 复发键：`EXTERNAL-CALL-RESILIENCE`
- 是否复发：第 N 次
- 关联记录：`2026-06-24-report-top10-gemini-child-no-retry.md`、`2026-07-07-mp3-cover-render-cdn-timeout.md`
- 防线层级：shared_guardrail / contract_test / observability

## 现象

火柴人视频任务 `52d937b0-6888-40db-b4ca-350c0a10e35e` 多次在“标题与正文分镜”
阶段失败，页面只显示“任务总超时”。其分镜子任务
`a709616d-405c-4775-b4ae-d7740c74ffa1` 从 12:54:46 运行至 13:09:56，
恰好在 900 秒固定总时限后失败。

## 影响

任务在任何分镜记录创建之前终止，图片、音频时间轴和视频合成都不能开始。Gem 已完成的
首轮回复没有写入 `gemini_storyboard.json`，因此页面的“复用 Gem 原文继续梳理”也无法使用，
每次只能从头请求并再次消耗约 15 分钟。

## 根因

分镜链路允许最多 12 轮“继续输出剩余正文”，单轮回复超时为 600 秒，但仍继承通用 Gemini
浏览器的 900 秒总时限。本次首轮回复接近 600 秒才完成，进入第一轮续写后只剩约 300 秒，
必然被总时限截断。

此外，通用 `generate` 只在所有续写和追问完成后写最终 JSON；虽然首轮响应已经成功获取并更新
数据库进度，异常路径仍会丢失内存中的 `turns` 和返回文本。架构上缺少逐轮 checkpoint，
导致可恢复的外部调用退化成不可恢复的全量重跑。

真实复跑还暴露了第二个终止条件缺陷：标题镜头把“标题：研报标题”放进
`【文案原句】`，正文续写又把“五”写成了数字“5”。已有内容对 1430 个去空白正文字符的
连续相似度达到 99.93%，但旧覆盖判断要求收集到的全部片段必须与正文完全相等。因此标题前缀、
一字符可修复漂移和重复尾段都会让流程继续无意义追问，直到再次撞上总时限。

横向检查同批三个任务又发现：worker 并发为 3，但同一个 Gemini profile 只能串行使用。
总时限从进入 `generate` 就开始计时，把等待前一个任务释放 profile 的时间也算作执行时间。
因此同批后启动的任务即使尚未打开 Gemini 页面，也可能已经耗尽大部分甚至全部预算。

最终真实复跑确认了最上游的耗时放大器：白板 Gem 的自定义指令要求每完成一个分镜就直接
调用图片工具。分镜阶段本应只返回文字和提示词，却被迫等待逐镜头生图；混合返回“文字 +
图片”时又不会进入仅图片恢复分支。Gem 改成纯文字后，1162 字任务约 75 秒即完成 38 个镜头，
且 `embedded_images=0`。

新 Gem 还暴露了两个格式兼容问题：偶发把 `【画面动作】` 写成 `【画面观察】`，以及在明确
输出 `【全文分镜完成】` 后仍因单字符遗漏继续重复整份分镜。重复内容会放大 normalizer 输入，
也会破坏提示词顺序校验。

## 解决思路

复用 MP3 长音频 Gemini 链路已经验证的长任务预算，不修改所有 Gemini 调用的全局默认值；
只为多轮分镜设置独立的响应和总时限下限。同时在通用 Gemini 生成器中按轮次保存原子
checkpoint，使后续超时至少保留已完成回复，可供查看、梳理或后续恢复。

## 实际方案

- 分镜 worker 的单轮回复预算下限最终提升为 1800 秒；真实伯恩斯坦任务证明续写可能超过
  900 秒，15 分钟不足以区分长回复和卡死。
- 分镜总预算下限最终提升为 7200 秒，并强制不少于“三轮单轮预算 + 300 秒页面开销”。
- 支持 `REPORT_VISUAL_PLAN_GEMINI_RESPONSE_TIMEOUT` 和
  `REPORT_VISUAL_PLAN_GEMINI_TOTAL_TIMEOUT` 独立覆盖。
- 首轮、每轮续写及普通追问完成后，立即原子写入 `gemini_storyboard.json`，状态标记为
  `partial`；最终成功后仍由原流程覆盖为完整结果。
- 浏览器续写终止条件允许标题镜头前缀和重复尾段；若完整正文连续窗口达到 99.5% 以上，
  停止继续请求并交给严格 normalizer。该容差只决定是否继续调用浏览器，最终保存仍必须由
  权威原文重建并通过 100% `covered_script_chars == source_script_chars` 校验。
- 超时错误带上实际秒数，避免后续只能从模糊的“任务总超时”反推阈值。
- 通用文本生成、图片生成和文件上传三条 Gemini 入口都在成功取得独占浏览器 context 后
  重新开始执行预算；profile 串行等待只作为排队时间展示，不再消耗远程执行硬时限。
- `report_visual_plan` worker 默认并发从 3 收敛为 1，使等待任务留在 broker，而不是三个线程
  同时争用唯一 profile；profile 锁默认等待上限也按调用总预算的三倍推导，不再固定为 1800 秒。
- 首轮和每次续写的外部提示词都明确禁止调用图片生成、绘图或图片编辑工具；分镜 Gem 本身也
  改为纯文字职责，图片仍由下游独立队列逐张生成。
- 识别 `【全文分镜完成】` 且标题/正文结构可解析时立即停止浏览器续写，避免完整结果被重复
  12 次；checkpoint 重试优先选择首个自包含完整轮次，而不是累积后的重复文本。
- 确定性解析器兼容 Gem 偶发的 `【画面观察】` 字段，并对接近 100% 的单字符遗漏使用权威
  原文重建分段边界；AI 图片提示词仍逐字取自 Gem，不允许 normalizer 改写。

- 新增逐轮 checkpoint 测试，验证首轮文本、turns 和 partial 状态原子落盘，临时文件不残留。
- 新增标题前缀、重复尾段及单字符可修复漂移的覆盖终止回归测试。
- 新增三条 Gemini 入口都在 profile context 获取后重置执行预算的契约测试。
- 新增分镜 worker 单并发及 profile 锁动态预算契约测试。
- Python 编译、`git diff --check` 和 Bug 记录严格检查通过。
- 只重载 `report_visual_plan` 专用 worker；全栈重启被安全门因活动中的知识星球发布任务阻止，
  未中断无关任务。
- 真实任务创建新分镜子任务 `6030447b-6e62-4db3-9203-74fb8b10afd0`：首轮完成后立即出现
  checkpoint，任务越过旧 900 秒故障点；前两轮 checkpoint 离线梳理得到 25 个正文分镜，
  `source_chars=1439`、`covered_chars=1439`。
- 正式“复用 Gem 原文继续梳理”成功，数据库写入 1 个标题镜头和 25 个正文镜头，子任务
  `status=succeeded`、`progress=100`、`segment_count=26`，父任务随后自动进入图片投递阶段。
- 横向检查伯恩斯坦、野村证券和高盛三个同批任务，其分镜子任务均为
  `storyboard_failed / 任务总超时` 且没有旧版 checkpoint；野村任务约 903 秒失败，另外两条
  因 profile 串行等待分别在约 20.9 和 27.2 分钟后失败，证明排队时间误计入预算。
- 首轮重跑进一步验证：伯恩斯坦取得两轮 checkpoint 后，第 2 次续写在 900 秒单轮上限失败；
  checkpoint 仅覆盖约 61% 原文，严格 normalizer 正确拒绝保存。同期野村和高盛虽未消耗执行
  预算，仍命中旧进程固定 1800 秒 profile 锁上限，促成单并发和锁预算的二次加固。
- 纯文字 Gem 最终三条复跑全部成功：伯恩斯坦 38 个镜头、1162/1162 字；野村证券 46 个镜头、
  1707/1707 字；高盛 49 个镜头、1352/1352 字。三条 `embedded_images` 均为 0，全部由
  确定性解析器保存，随后才独立投递下游图片任务。

## 复发预防

1. 多轮外部调用的总预算必须由单轮预算和最大必要轮次推导，不能独立使用更小的固定默认值。
2. 外部 AI 每完成一个有业务价值的轮次必须持久化 checkpoint，不得等全部链路结束才保存。
3. 业务特有的长任务预算使用特有环境变量，避免为了一个长链路无边界放大全局超时。
4. 真实验收同时核对耗时、当前步骤、checkpoint 文件和最终结构化分镜，不能只看 Celery 成功。
