# MP3 手动 DS 的“起点/终点”被严格规划误拒绝

## 基本信息

- 状态：RUNTIME_REPLACED/OBSERVING（生产规划、详情展示和完整成片均已验收；待后续窗口确认未复发）
- 严重级别：P1
- 影响模块：mp3_video_workflow / 手动 DS 返回值 / 标题与时间轴解析
- 首次发现：2026-08-26，任务 `4db74792-b261-49e6-9ed1-fff21c86b83b` 在 58% 失败；同批历史任务 `8d13af3b-2074-4ce3-a3f9-d1be43ae602a` 和 `95ada928-334a-4133-9f73-649ce426b9ae` 命中相同复发键
- 修复提交：待提交

## 现象

详情页已经从同一份 DS 原文展示 `03:57 - 52:33` 和有效标题，worker 却报告缺少有效结束时间戳及非占位文案，并在视觉生成前停止。重复点击续跑只会重复同一失败。

## 影响

- 合法的手动 DS 返回值无法进入封面、关键帧和视频阶段。
- 详情展示和生产规划对同一输入得出相反结论，用户无法判断应修改 DS 还是重试。
- 无根因修复的重复投递形成失败风暴，并浪费 worker 容量。

## 根因

生产规划的 `extract_audio_range` 只识别“开始/起始”和“结束/截止/终止”，未识别本次 DS 使用的“起点/终点”。标题解析又未过滤“标题（主版本……）”“不同角度标题版本（……）”“标题优化另一版本（……）”等描述性栏头，导致栏头进入严格占位检查。第 7 条合法竖屏标题还使用了 `|` 分隔正文、`/` 分隔日期，旧逻辑会把栏头拼入标题后才勉强通过格式检查。

第三个历史失败任务暴露了同一簇的第二种输入形态：DS 七段内容完整但完全没有 `1.`–`7.` 编号，只使用“标题（主版本）”“黄金片段”“小君君横屏标题”等描述性标题。DeepSeek 当时返回 HTTP 402 后进入本地降级路径，旧 `_direct_ds_numbered_sections` 得到空映射，通用标题兜底又把“格式）”栏头当成正文。页面因此把 1/2/6/7 显示为“未识别”，生产侧则在 58% fail-closed。

## 解决思路

保持严格 fail-closed 契约，不降低必填字段和占位文案检查；只统一合法标签、描述性栏头及末尾日期分隔符的确定性解析。

## 实际方案

- 时间范围解析增加“起点/终点”标签。
- 描述性标题栏头进入统一 heading 过滤，包括“标题优化另一版本”。
- `_direct_ds_numbered_sections` 在没有任何数字编号时，按锚定的描述性标题确定性映射到 1–7；有数字编号时继续走原解析，禁止模糊混合猜测。
- 竖屏标题仅在斜杠紧邻合法日期时将其规范为竖线，禁止接受任意混合分隔格式。
- 加入来自现场输入形态的回归测试；用任务保存的原始 DS 再次通过严格规划校验。

## 复发预防

- DS 展示解析与生产规划新增标签时必须同时增加同形输入的契约测试。
- 降级解析必须同时覆盖编号段落与无编号描述性段落；unit test 禁止真实调用外部 AI provider。
- 任何描述性栏头不得进入视觉文案；任何分隔符兼容必须限定在可验证的结构位置。
- 同一错误重复投递前必须先验证解析结果发生变化，避免失败风暴。
