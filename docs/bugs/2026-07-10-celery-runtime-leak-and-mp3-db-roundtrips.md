# 2026-07-10 Celery 运行时泄漏与 MP3 编排重复数据库往返

## 基本信息

- 状态：修复已部署，等待真实业务负载验收
- 严重级别：高
- 影响模块：Flask app factory、Celery workers、数据库日志、MP3 视频编排、发布渲染
- 首次发现：用户多次反馈同类慢查询长期反复出现
- 修复提交：待提交

## 现象

- `publication_tasks` 单行查询反复读取 `params/result`，偶发耗时 1-31 秒。
- 2026-07-10 10:56 的一轮 MP3 父编排只推进已有子任务，仍耗时 29.51 秒；日志中连续出现多次单行 SELECT，单次约 370-835 ms。
- 同一条 SQL 在同一时间出现多条耗时略有差异的慢查询记录。
- `mp3_video_workflow` worker 一度有 103 个线程，`report_video` worker 一度有 38 个线程。
- 过去多次修改以代码测试或索引存在作为完成依据，没有在新进程和真实负载下验证同一 SQL 指纹是否消失。

## 影响

- 编排状态推进被大量无业务价值的数据库往返拖慢。
- 重复 SQL 监听器放大日志数量，导致慢查询统计失真并掩盖真正的查询次数。
- 每任务增加后台线程，长期运行会增加内存、调度和日志轮转竞争。
- 用户无法根据“已修复”判断实际运行状态，工程验收失去可信度。

## 根因

### 运行时初始化泄漏

每个 Celery 任务都会调用 `create_app()`。旧实现每次调用都会：

- 启动 performance monitor 后台线程；
- 启动日志维护后台线程；
- 向 SQLAlchemy `Engine` 重复注册数据库事件监听器。

这些动作应按进程执行一次，却按任务执行一次。重复监听器使一条真实 SQL 被记录多次，重复线程则随任务数持续增长。

### MP3 编排 SELECT-before-UPDATE

MP3 编排的 `_emit`、`_update_result` 和 `_record_child` 每次状态更新都先读取整个 `result` JSON，再由本机合并并写回。父编排在一轮任务中多次调用这些函数，远程数据库链路的单次 JSON 往返延迟被成倍放大。

测量结果显示，热点任务 `result` 的文本大小约 45-56 KB；主键查询的 PostgreSQL 执行计划仅 0.040 ms，但客户端完整取回同一行通常需要 150-1300 ms，并有 16-31 秒异常尖峰。因此索引不是这个 SQL 的根因，减少网络往返才是必要措施。

## 实际方案

- Web 专用后台线程不再由 Celery、scheduler、watchdog 和测试进程启动。
- performance monitor、日志配置、日志维护线程和 SQLAlchemy 监听器全部改为进程级幂等。
- 慢查询日志增加 PID、进程角色和代码调用位置。
- MP3 `_emit`、`_update_result`、`_record_child` 改为 PostgreSQL 端原子 JSONB 更新，不再 SELECT-before-UPDATE。
- 单轮 MP3 编排增加作用域内结果缓存；复用判断读取本轮已加载状态，落库仍执行原子 SQL，不以缓存替代数据库。
- MP3 API 的任务读取不再使用会受 identity map 影响的 `Query.get()`。
- MP3 详情页刷新 B 站上传状态时改用轻量 `/bilibili-uploads` 端点；轮询只读取父任务归属投影列和上传子任务，不再读取父任务 `params/result`。
- publisher 和 Gemini 进度更新的同类 SELECT-before-UPDATE 路径同步收敛。
- B 站上传在读取平台凭据后、进入长耗时网络调用前显式释放数据库 session，避免 `idle in transaction` 持续整个上传过程。

## 复发预防

- 数据库性能修复必须遵守 [数据库性能修复验收纪律](../rules/database-performance-acceptance-discipline.md)。
- `create_app()` 内新增线程、timer、event listener 或 scheduler 时，必须说明进程角色和幂等边界，并补重复初始化测试。
- 热状态更新禁止默认采用“SELECT 大 JSON -> 本机合并 -> UPDATE”；优先使用结构化列、原子 SQL 或专用子表。
- 慢查询统计必须先按 PID、调用位置和 SQL 指纹去重，不能把重复监听器输出当成真实查询次数。
- 没有重启边界和真实业务负载证据时，只能表述为“代码已修改”或“已部署待验收”，不得表述为“已解决”。
