## 现象

洪灝和生财有术全部 Tab 计划均处于启用状态，但数据库公网白名单失效期间，
到期触发在凭据查询阶段失败。数据库恢复后，调度器重新读取数据库配置并把两条计划
统一重排到恢复时间后三小时，没有立即补偿失败轮次，用户看到同步长时间没有推进。

## 影响

- 两个星球从最后成功轮次到下一次重排之间形成同步空窗。
- 邮件会报告数据库触发失败，但数据库恢复本身不会推动业务追赶。
- 状态文件中的失败结果仍然存在，计划展示的下一次时间却已被刷新，容易误以为失败已被处理。

## 根因

调度循环能在数据库不可用时退回 bootstrap 配置，也能在数据库恢复后刷新 schedule，
但只把新任务的 `next_run` 设为“当前时间 + interval”。代码没有保存配置来源的降级状态，
也没有识别 `bootstrap_fallback -> database` 这一恢复边界，因此没有补偿动作。

## 解决思路

把配置来源纳入调度签名并显式记录当前是否处于降级状态。只有观察到真实的
`degraded -> database` 转换时才执行一次补跑；普通启动和普通配置变更不补跑，避免重复投递。
实际业务入口继续复用全部 Tab 服务既有的进程锁和 active-run 幂等保护。

## 实际方案

- 调度签名增加配置 `source`，使数据库恢复能被可靠识别。
- 新增运行时 schedule 刷新入口，集中处理签名变化和恢复边界。
- 数据库恢复后以 `scheduler_db_recovered` 触发一次全部 Tab 同步。
- 保留原有 active run 检查、文件锁和每目标错误收口逻辑。

## 验证

  - 覆盖数据库降级恢复后立即补跑。
  - 覆盖普通 schedule 初始化/刷新不补跑。
- `tests/unit/test_zsxq_all_tabs_auto_sync.py`
  - 继续覆盖全部 Tab 配置、幂等和投递合同。
- 定向结果：`20 passed`。

现场数据库已于 08:45 恢复。真实补跑仍被失效的知识星球 Cookie 阻塞：
指定凭据只包含分析 Cookie，环境变量旧 Cookie 对三个目标星球均返回 401。

## 复发预防

- 所有周期调度器的降级配置必须携带来源标识。
- 恢复时不能只重算下一次执行时间；必须明确选择补跑或记录放弃原因。
- 恢复补跑必须复用业务幂等入口，不能绕过 active-run/锁保护直接创建重复任务。
