# ZSXQ Lab 专属组操作区泄漏到普通组

## 基本信息

- 状态：已修复
- 严重级别：P1
- 影响模块：ZSXQ Lab / 人工下载计划 / 分组切换
- 首次发现：2026-07-14
- 修复提交：当前工作区
- 根因分类：业务作用域守卫分散，重绘函数绕过 Group 约束
- 复发键：ZSXQ-GROUP-SCOPE-GUARD
- 是否复发：既有产品约定的回归
- 关联记录：无
- 防线层级：shared_guardrail / contract_test

## 现象

切换到普通知识星球组后，页面仍展示附件筛选、全选附件、创建下载计划、下载上限和清洗后自动发布等“前沿信息收录”专属操作。

## 影响

普通组界面出现不适用且具有副作用的批量操作，用户可能误建下载、清洗或发布任务；同时页面行为与已确认的产品规则不一致。

## 根因

页面切组时已经按 Group ID 控制过系统同步区，但附件加载完成后，`updateBatchDownloadButton()` 只根据是否存在附件决定显示控件，没有再次校验当前 Group。后执行的通用重绘覆盖了先前的隐藏状态，主题和附件选择框也没有绑定相同的业务作用域。

## 解决思路

把 Group 约束放到所有可能改变专属操作状态的入口，并在服务层进行最终校验，避免仅依赖一次性的页面隐藏。

## 实际方案

- 增加统一的 `hideManualDownloadControls()`，普通组切入和重绘时都清空选择并隐藏专属控件。
- 主题、附件选择框仅在 Group ID `28888112822211` 下渲染。
- `updateBatchDownloadButton()`、`updateSelectAllButton()` 和 `createManualDownloadWorkflow()` 均 fail closed。
- 后端 `_build_manual_download_snapshot()` 拒绝非“前沿信息收录”组创建人工计划。
- 更新前端脚本版本，避免浏览器继续使用旧缓存。

## 验证

- JavaScript 语法检查通过。
- 前端契约测试覆盖 Group 常量、重绘守卫、直接操作守卫和选择框条件渲染。
- 服务层单元测试验证普通组无法创建人工计划。
- `git diff --check` 通过。

## 复发预防

以后所有 Group 专属能力必须同时具备：统一可见性函数、每个异步重绘入口的作用域判断、服务端业务边界校验、针对非目标 Group 的契约测试。不能只在切组事件里隐藏一次。

## 后续事项

- 如果未来要向其他组开放人工计划，应改为显式能力配置列表，不应删除服务端守卫或把逻辑退化为“有附件就显示”。
