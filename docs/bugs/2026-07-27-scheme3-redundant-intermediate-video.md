## 现象

真实任务 `27679563-79c1-4dba-a340-753faa1bbef8` 已有整篇 WAV，关联视觉任务
`52d937b0-6888-40db-b4ca-350c0a10e35e` 的 25 张正文分镜图片也已全部完成。
用户只选择方案三生成完整竖屏时，系统仍失败并提示：

```text
方案三需要先完成顶部所选的火柴人或哆啦A梦视觉视频
```

这迫使用户先把分镜图片和音频编码成一份 16:9 视觉 MP4，再由方案三解码这份
MP4、嵌入 9:16 模板并重新编码。

## 影响

- 方案三在素材齐全时仍被错误阻塞。
- 只需要方案三时多做一次完整视频编码，增加等待时间、CPU/GPU 消耗和磁盘占用。
- 二次有损编码降低中央视觉区域的清晰度。
- 视觉工作流的逐镜时间轴未生成时，25 张已完成图片也不能被复用。

## 根因

### 代码层

1. API 的方案三预检只调用 `_linked_visual_video_path`，把“完整视觉 MP4 存在”作为唯一就绪条件。
2. 前端只选择 `status=succeeded && video.url` 的视觉任务，忽略“正文图片全部完成”的任务。
3. Publisher 的方案三分支只接受 `visual_video_path`，没有直接消费分镜图片时间轴的入口。
4. 既有 FFmpeg 合成器只支持“模板背景 + 内容视频”，不支持“模板背景 + 图片序列 + 整篇音频”。

### 架构层

系统把可选的兼容产物（完整 16:9 MP4）误当成方案三的必需源素材。方案三真正需要的
最小合同是：

- 整篇音频；
- 全部正文分镜图片；
- 可用的镜头时间分配。

时间轴应当可以由已对齐数据提供，也可以在没有对齐结果时由正文文案权重确定性生成，
不应强迫另一个成片工作流先完成。

## 解决思路

- 方案三优先使用分镜图片和整篇音频一次合成。
- 已有逐镜音频时间轴时原样复用；缺少时间轴时按各镜头正文字符数分配整篇音频时长，
  最后一镜精确收口到音频终点。
- 保留原 `visual_video_path` 分支，兼容历史任务和已存在的视觉 MP4。
- 10 秒预览截取真实时间轴开头，不把全部镜头压缩进 10 秒。
- 同 PDF、同可见用户的所有权校验仍在 API 内完成，客户端不能提交任意文件路径。

## 实际方案

- API 新增同 PDF 分镜素材解析与确定性时间轴构建。
- 视觉任务列表增加 `scheme3_ready` 与正文图片完成摘要。
- 详情页允许选择“正文图片全部完成但视觉 MP4 尚未完成”的视觉任务。
- Publisher 优先调用分镜直出合成器，旧视觉视频作为兼容兜底。
- VideoEditor 新增单次 FFmpeg 管线：
  - 循环输入每张分镜图片；
  - 按镜头时长拼接；
  - 嵌入方案三中央 16:9 框；
  - 同一轮完成字幕烧录、整篇音频复用与最终 MP4 编码。
