# Gemini 登录失效人工恢复设计

## 目标

当研报分镜使用的 Gemini 浏览器 Profile 登录失效时，系统停止无效自动重试，将分镜和父工作流明确标记为“等待人工登录”，发送包含可执行解决步骤的去重邮件，并允许用户完成登录后恢复原分镜任务。

## 方案选择

采用专用状态 `blocked_by_login`。继续使用 `failed` 会让用户误以为任务不可恢复；复用 `blocked_by_captcha` 会混淆登录失效与安全验证，也无法给出准确操作说明。新状态沿用现有 `PublicationTask.status` 字符串字段，因此不需要数据库迁移。

## 架构与数据流

1. Gemini 浏览器检测登录页，保存截图并发送人工介入邮件。
2. 浏览器抛出结构化 `GeminiBrowserHumanInterventionError`，携带 `reason=login`、通知结果、Profile、页面及截图信息。
3. 分镜 Celery 任务识别该异常，不执行自动重试，写入 `blocked_by_login`，并将人工介入信息保存到任务 `result`。
4. 父视频工作流同步为 `blocked_by_login / storyboard_blocked_by_login`，页面显示“等待人工登录”，不继续轮询为运行中。
5. 邮件给出指定 Profile、Gemini 页面、截图、工作流链接以及登录验证步骤。相同 Profile 和原因在默认 30 分钟内只发送一次。
6. 用户登录后点击“登录完成，恢复任务”。恢复 API 原子地把原分镜任务和父任务改回排队状态，并重新投递同一个任务 ID；源文案、提示词和已有文件保持不变。

## 恢复安全性

- 恢复接口只接受 `blocked_by_login`，避免误重跑普通失败、已完成或正在运行的任务。
- 入队前生成新的 Celery task ID；状态更新与投递失败都有明确回滚结果。
- 老的 Celery 投递由现有 stale-delivery 校验拒绝，避免并发重复执行。
- 邮件发送失败不会覆盖登录失效根因；发送结果写入任务结果并在页面可见。

## 邮件操作手册

邮件必须明确告诉处理人：

1. 关闭正在占用邮件所列 Profile 的自动化 Chrome 窗口。
2. 使用邮件所列浏览器 Profile 打开 Gemini 页面。
3. 登录 Google/Gemini，并完成验证码或安全验证。
4. 确认 Gemini 输入框可见且能进入目标 Gem。
5. 返回邮件中的工作流详情页，点击“登录完成，恢复任务”。
6. 若仍失败，核对邮件中的截图、页面 URL、Worker 和 Profile，再处理对应浏览器实例。

## 错误与可观测性

- 邮件未启用、缺少配置、冷却去重或发送失败，均保留在 `result.human_intervention.notification`。
- 任务页面展示通知是否成功；未发送时提示用户直接按页面步骤处理。
- `blocked_by_login` 是可恢复终态，watchdog 不应把它当作遗失队列任务自动补投。

## 测试

- 通知正文包含具体登录步骤、Profile、截图和工作流链接，且继续满足冷却去重。
- 登录检测抛出结构化人工介入异常并携带通知结果。
- 分镜登录失效写入子任务及父任务阻塞状态。
- 恢复接口只恢复登录阻塞任务，并重新投递相同任务 ID。
- API 状态映射和详情页正确展示 `blocked_by_login`、操作步骤及恢复按钮。
