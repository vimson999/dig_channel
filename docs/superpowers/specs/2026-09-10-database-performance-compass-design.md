# 数据库性能罗盘设计

日期：2026-09-10

状态：书面规格待复核

## 背景

项目目前把应用日志里超过阈值的数据库调用统称为“慢 SQL”。这个词混合了四类性质不同的问题：PostgreSQL 执行慢、应用到数据库的往返慢、Session/事务占用过久，以及 N+1、宽载荷或高频轮询造成的查询放大。

这种混用会产生两个后果：执行计划已经很快时仍反复加索引；真正的连接等待、事务跨外部 I/O 或查询次数问题则迟迟不能归到唯一责任人。结果是同一问题以不同入口和不同 Bug 记录反复出现，看起来“总也改不完”。

本设计建立一个持久化的“数据库性能罗盘”，让诊断、修复、验收、日报和复发登记共享同一套分类与关闭口径。

## 目标

1. 对每个数据库性能事件给出一个主分类、可选促成因素和可复核证据。
2. 把应用端 SQL 往返耗时与 PostgreSQL executor 耗时明确分开。
3. 为四类问题定义允许动作、禁止动作、责任边界和 CLOSED 条件。
4. 让分析器、规则文档、日报、Bug 记录和复发注册表引用同一事实来源。
5. 证据不足时明确输出 `DB_UNKNOWN`，不靠猜测制造根因。

## 非目标

- 本次不修改生产数据库、PgBouncer 配置、网络拓扑或运行进程。
- 本次不新建监控平台，不引入新的 metrics 后端或强制启用 `pg_stat_statements`。
- 本次不重写历史报告；历史结论只在被重新打开时按新罗盘补充分类。
- 罗盘不替代具体 Bug 记录、执行计划和真实运行验收。

## 核心术语

### 应用 SQL 往返耗时

从应用/驱动发起数据库调用到调用返回的墙钟时间。它可能包含连接池等待、网络、PgBouncer、锁等待、PostgreSQL 执行、结果传输和客户端解码。

现有日志里的 `slow_sql` 阈值只说明“应用观察到一次较慢的数据库往返”，不能单独证明 SQL 执行计划慢。对外展示统一改称“应用 SQL 往返延迟”；为兼容已有日志和测试，可以暂时保留内部字段名或输入标签 `slow_sql`。

### PostgreSQL executor 耗时

同一查询、可比较参数和足够接近的数据状态下，由 PostgreSQL 执行证据证明的服务器端耗时。首选证据是 `EXPLAIN (ANALYZE, BUFFERS)`；必要时辅以锁等待、活动会话、I/O 和统计快照。

### 主分类与促成因素

每个事件只能有一个主分类，避免同一事件在报表中重复计数。其他已证明因素记录为 `contributors`。无法决定主分类时使用 `DB_UNKNOWN`，不得选择“看起来最像”的类别。

## 分类模型

### `DB_EXECUTOR`：PostgreSQL 执行慢

适用条件：服务器端执行证据能够解释应用观察到的主要耗时，或计划显示高代价扫描、排序、堆访问、行数估算偏差、锁等待、I/O 等数据库内部瓶颈。

允许动作：改写查询、补充或调整索引、更新统计信息、控制扫描与返回集合、处理锁/I/O/膨胀，并保存变更前后的可比计划。

禁止动作：只凭应用日志超过 1 秒就加索引；在已有正确同形索引时继续创建重复索引；用单次空闲窗口的快速计划宣布问题已解决。

主责任：查询及数据模型所有者；锁、存储或维护问题由数据库运行责任人共同负责。

CLOSED 条件：可比场景的服务器端证据达到目标，应用端真实负载也达到验收指标，业务完整性无回退，后续窗口无同复发键重现。

### `DB_ROUND_TRIP`：连接池、网络或驱动往返慢

适用条件：应用 SQL 往返明显慢于可比较的服务器端执行，且连接池等待、PgBouncer、网络/TLS、结果传输或驱动行为能够解释差值。

允许动作：采集 checkout 到调用返回的分段时间；关联 PgBouncer pool/server、连接错误和网络事件；调整有证据支持的连接生命周期、池策略、超时或部署拓扑。

禁止动作：用索引修复连接冷启动或隧道抖动；只提高全局 timeout；用无限 SQL 重试掩盖连接故障。

主责任：数据库连接基础设施和应用平台所有者；查询所有者负责提供可比较的 executor 基线。

CLOSED 条件：连接/网络异常指标和应用往返尾延迟在真实负载下同时达标，executor 基线未恶化，并通过后续完整窗口复核。

### `DB_SESSION_HOLD`：Session 或事务持有过久

适用条件：数据库 Session、连接或事务跨越了外部 HTTP、文件 I/O、sleep、broker、模型调用、长 CPU 阶段或不必要的业务等待；主要成本来自占用时间而非单条 SQL 执行时间。

允许动作：缩短事务边界；在外部 I/O 前 commit/rollback 并 remove Session；跨边界只传标量、不可变 Row/DTO 或必要快照；采集 checkout/checkin、事务开始/结束和非 SQL 区间。

禁止动作：在 commit/rollback 后继续依赖 ORM 实体；用扩大连接池掩盖长时间持有；只优化事务内某条快速 SQL。

主责任：持有 Session/事务的业务工作流所有者。

CLOSED 条件：目标路径的 Session/事务持有时间满足预算，外部 I/O 不再位于持有区间，故障和重试路径也符合边界，真实并发验收不再耗尽连接。

### `DB_QUERY_AMPLIFICATION`：查询次数或载荷放大

适用条件：查询次数随实体数、子任务数或轮询次数增长；同一阶段出现重复指纹；热路径读取大 JSON/大文本/多行宽载荷；或多个消费者重复加载同一结果。此类失败不受单条查询时长阈值豁免。

允许动作：集合查询、结构化投影、批量预取、一次物化后传递有界快照、拆分热冷数据、定义每页/每阶段查询次数和列/字节预算。

禁止动作：因为每条查询低于 1 秒就忽略 N+1；仅靠缓存隐藏未受控查询；删除业务必需字段来降低载荷。

主责任：产生查询形状和调用频率的业务能力所有者。

CLOSED 条件：SQL 捕获测试和真实流程同时满足次数、所选列及载荷预算；主体、异常、重试和终态消费者均覆盖；业务结果完整。

### `DB_UNKNOWN`：证据不足

适用条件：只有应用端耗时，没有可比较 executor 证据、连接/池快照、Session 生命周期或调用次数证据；或者证据来自不同参数、不同数据规模、不同部署窗口，不能可靠归因。

允许动作：保留原始时间窗、指纹、参数形状和进程边界，列出缺失证据并安排定向采集。

禁止动作：把 `UNKNOWN` 当作可以忽略；在补齐证据前执行索引、池配置或事务结构变更；把“没有看到错误”写成“已解决”。

主责任：事件发现者负责补齐可归因证据；补齐后转交明确所有者。

CLOSED 条件：`DB_UNKNOWN` 本身不能 CLOSED；必须重分类，或以证据证明原事件无效并记录排除原因。

## 判定顺序

分类按以下顺序进行，防止拿单一阈值代替归因：

1. 验证样本完整性：时间窗、PID/启动时间、SQL 指纹、调用路径、参数形状和业务场景是否可比较。
2. 检查查询放大：是否存在 N+1、轮询累积、重复指纹、宽行或宽 JSON。若放大本身足以解释问题，主分类为 `DB_QUERY_AMPLIFICATION`。
3. 检查 Session 生命周期：是否跨外部 I/O 或业务等待持有连接/事务。若占用而非 SQL 是主要矛盾，主分类为 `DB_SESSION_HOLD`。
4. 比较 executor 与应用往返：服务器端耗时可解释主要延迟时为 `DB_EXECUTOR`；executor 快而应用往返慢时，继续核对连接池、PgBouncer、网络、传输和驱动证据。
5. 连接链路证据能解释差值时为 `DB_ROUND_TRIP`；否则为 `DB_UNKNOWN`。

优先顺序不是严重性排序。若同一事件同时存在多种问题，只选择对该事件贡献最大的已证明因素为主分类，其他因素放入 `contributors` 并分别建立验收项。

## 证据和阈值纪律

- 现有 1 秒阈值继续作为应用侧观察门槛，不作为根因阈值。
- `EXPLAIN (ANALYZE, BUFFERS)` 小于 100ms，而同场景应用往返超过 1 秒且相差至少 5 倍时，不得把 `DB_EXECUTOR` 作为主分类，除非异常窗口另有锁或 I/O 证据。
- 服务器端执行超过 500ms，或虽低于 500ms但占应用耗时的大部分并显示明确计划缺陷时，可列为 `DB_EXECUTOR` 候选；最终仍需可比证据确认。
- N+1、`multirow_payload`、JSON 热路径和持续轮询属于查询形状失败，不受 1 秒阈值豁免。
- Session 持有以业务边界和并发预算判断，不用某个全局秒数一刀切。每个能力必须声明自己的连接持有预算。
- 所有阈值都用于引导取证，不得绕过真实负载验收和业务完整性检查。

## 分析器输出契约

`scripts/diagnostics/analyze_db_performance_logs.py` 后续按以下契约演进：

1. 保留既有输入兼容能力和原始计数，避免历史日志失读。
2. 用户可见文案把 `slow_sql` 解释为“应用 SQL 往返延迟”，不再直接写成 PostgreSQL executor 慢。
3. 增加分类汇总，至少输出 `category`、`evidence`、`missing_evidence` 和 `confidence`。
4. 自动分类只使用日志中存在的事实。缺少关键证据时输出 `DB_UNKNOWN`，不推断连接、锁或索引根因。
5. 同一事件只进入一个主分类计数；促成因素单列，不加入主分类总数。
6. 原始 SQL/参数继续遵守脱敏和长度预算，分类功能不得扩大敏感信息暴露。

本阶段不承诺新增稳定公共 JSON API；先锁定人类可读输出和内部分类函数，避免在证据模型未稳定时扩大兼容面。

## 持久化与单一事实来源

实施后，知识按以下层次持久化：

- `docs/rules/database-performance-compass.md`：规范性事实来源，保存分类、判定顺序、动作边界和关闭条件。
- `docs/rules/database-performance-acceptance-discipline.md`：保留发布与验收纪律，引用罗盘而不复制分类正文。
- `scripts/diagnostics/analyze_db_performance_logs.py`：执行分类契约，输出事实与缺口。
- `tests/unit/test_db_performance_log_analyzer.py`：锁定分类、术语、单主分类和 `DB_UNKNOWN` 行为。
- `docs/bugs/README.md` 与日报模板：要求每个性能条目填写罗盘分类、证据、所有者、阶段和阻塞项。
- `docs/bugs/recurrence-registry.json`：对开放或复发问题记录稳定复发键、根因分类、验收阶段和阻塞证据。
- 自动化 memory：只记录本轮观察、分类变化、待补证据和下一步，不把短窗口无异常持久化为 CLOSED。

规则文档是规范，分析器是实现，Bug/日报/registry 是实例。实例与规范冲突时，以规则文档为准并修正实例；分析器与规则冲突视为测试失败。

## 数据流

```text
应用/数据库/PgBouncer 日志
          │
          ▼
原始事实提取与窗口校验
          │
          ▼
放大 → Session 持有 → executor/往返差值 → 连接链路
          │
          ▼
一个主分类 + contributors + 缺失证据
          │
          ├── 日报与 Bug 记录
          ├── recurrence registry
          └── 验收与后续窗口复核
```

## 兼容与迁移

- 已有 `slow_sql` 原始日志、测试夹具和历史报告无需立即重写。
- 新输出先增加明确解释与分类汇总；内部旧键只为输入兼容保留，不再作为根因名称传播。
- 当前开放的数据库性能 Bug 在下一次触达时补充罗盘分类；不批量篡改已经封存的历史记录。
- 若一个旧 Bug 混有多个独立根因，保留稳定复发键，并在记录内拆成一个主分类和多个有独立验收条件的促成因素。

## 验收标准

1. 四个已知类别和 `DB_UNKNOWN` 都有单元测试样本。
2. 同一事件不会同时计入两个主分类。
3. “应用 SQL 往返延迟”与“PostgreSQL executor 耗时”在规则、分析器和报告模板中含义一致。
4. 只有应用端慢日志时，分析器不会建议加索引，而是输出缺失的 executor/连接证据。
5. N+1 或宽载荷即使单条低于 1 秒，仍归为 `DB_QUERY_AMPLIFICATION`。
6. Session 跨外部 I/O 的样本归为 `DB_SESSION_HOLD`，不因其中某条 SQL 较慢而丢失生命周期根因。
7. 现有分析器回归测试、完整 unit、compileall、Bug strict、registry JSON 和 `git diff --check` 全部通过。
8. 不修改生产数据库、不重启运行进程、不执行结构迁移。

## 失败处理

- 日志格式未知或字段缺失：保留可解析事实，输出 `DB_UNKNOWN` 和缺失字段，不让整个审计失败。
- 证据互相冲突：降低 confidence，记录冲突，不自动选择更方便修复的类别。
- 规则与实现不一致：测试必须失败，状态保持未验收。
- 真实运行结果与实验相反：重新打开原复发键，保留原分类历史，按新证据重分类，禁止新开临时记录来重置次数。
