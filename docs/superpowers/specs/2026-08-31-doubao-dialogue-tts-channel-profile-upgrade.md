# Doubao Dialogue TTS 频道 Profile 升级设计

## 目标

在保留 `doubao-dialogue-tts` 通用能力的前提下，让当前项目默认加载“小君君”频道 Profile。用户在本项目中只提交研报和初步解析时，也能稳定得到固定开场、正确作者称呼、面向洪总听众的解释型文案，以及已验证的双声线参数。

该 Profile 只属于当前项目，不成为全局 Skill 的通用默认。

## 已确认范围

- 通用 Skill 继续支持其他频道和临时主持人。
- 当前项目通过项目配置自动选择 `xiaojunjun-honghao` Profile。
- 本次不调用豆包 TTS API，不重新生成音频。
- 本次可以修改 Skill 指令、Profile 资源、manifest 规范和本地预检脚本。
- 用户仍可在单期任务中明确覆盖项目默认 Profile 或语音参数。

## 术语边界

“收费”必须区分为两件事：

1. **API 计费边界**：最终文案、manifest 和 dry-run 通过，用户看到发送文本、模型、声线、字符数、输出位置和第三方数据传输说明并明确授权后，程序发出第一条真实豆包 TTS 请求。审稿、dry-run、缓存复用和本地合并不产生新的 TTS 请求。
2. **内容付费节点**：节目中免费试听切换到付费内容的时间戳。它只能依据最终音频时间轴判断，不能用固定百分比或文案字数代替。

## RED：旧版基线

2026-08-31 使用当前 Skill 做了三组无网络、无付费基线测试。

### 场景一：用户只给研报

旧版自行创建了不存在的《宏观研报精读》频道，开场为“大家好，欢迎来到《宏观研报精读》”，没有加载“小君君”固定开场，并在主持人口播中直呼“洪灏”。

### 场景二：初稿诱导纠错

旧版虽然保留了锁定原文，但主持人口播写成“这里的重点不是……”“洪灏也没有作出……”“更准确的理解是……”，仍带有替作者纠偏和审稿的姿态；同时缺失固定开场并直呼全名。

### 场景三：用户未重复提供语速

旧版把清澈和刘飞都设为 `1.00`，并声称这是频道默认值。它正确守住了 API 授权边界，但 dry-run 摘要没有显示已加载的频道 Profile，也没有项目默认参数来源。

以上失败证明，问题不是单次文案疏漏，而是当前 Skill 缺少可持久加载的项目 Profile 和确定性预检。

## GREEN：新版复测

使用相同三组请求读取 staging 新版 Skill 后：

- 人设场景自动解析 `xiaojunjun-honghao`，使用固定开场，主持人口播统一称“洪总”，解读围绕风险溢价机制和观察变量展开；
- 纠错诱导场景把事实核验留在非口播审校注，主持人口播改为解释“重新评估”的条件含义，没有把节目写成对作者的挑错；
- 运行时场景 dry-run 显示项目默认 Profile、清澈 `1.08`、刘飞 `1.00`、参数来源、API 计费边界和未发生外部传输状态；
- 三组复测均未调用网络或 TTS API。

## 方案

### 1. 通用核心

`SKILL.md` 只保留共享流程和路由规则：

- 从当前工作目录、来源或 manifest 所在目录向上查找项目配置；
- 本次任务显式 Profile 优先于项目默认；显式 `generic` 可停用项目默认；
- 只有命中具体 Profile 时才读取对应 Profile 资源；
- 作者观点优先，主持人的产出目标是增加理解；
- 文案确认与付费 TTS 授权是两个独立状态。

### 2. 项目默认选择器

项目根目录新增 `.doubao-dialogue-tts.json`，只保存：

- 配置 schema；
- 默认 Profile ID：`xiaojunjun-honghao`。

配置不复制人设全文，也不保存密钥或任务内容。

### 3. 小君君 Profile

Skill 的 `references/channel-profiles/` 中保存结构化 Profile，作为编辑和预检的共同来源：

- 主持人：小君君；
- 固定开场；
- `洪灏 -> 洪总` 的主持人口播称呼映射；
- 受众：洪总的长期听众与粉丝；
- 关系：帮助理解作者，而非审稿、挑刺或抢结论；
- 正向解读契约：定位原句作用，解释机制，连接上下文，给出条件或观察变量；
- 禁止进入口播的后台表达；
- 清澈 `1.08`、刘飞 `1.00` 的默认声线参数；
- 简洁结尾、无点赞订阅和模板化免责声明；
- 插入点数量由逻辑增量决定，不设置固定数量。

### 4. Manifest 与预检

manifest 可记录 `editorial.profile_id`，但当它缺省时，预检程序应自动解析项目默认。预检摘要必须显示：

- Profile ID 及其来源；
- 双方 voice ID、标签和最终生效语速；
- 逻辑段数和字符数；
- API 计费边界与第三方数据传输状态。

Profile 激活时，预检执行以下确定性检查：

- 第一段主持开场以固定句开头；
- 主持人口播不得直呼被映射的作者全名，锁定原文和元数据不受影响；
- 主持人口播不得包含“原文没动”“事实核对”“底稿校正”“按要求保留”等后台语言；
- Profile 默认声线和语速在缺省时自动补齐；显式单期覆盖保留，并在摘要中标记来源；
- 通用模式不受小君君规则污染。

对“是否真正增加理解”的判断仍由编辑质量门完成，不用关键词扫描冒充语义判断。

## 验收标准

- 当前项目中只给研报也能自动解析 `xiaojunjun-honghao`。
- 固定开场、洪总称呼、解释型关系和语速默认全部可追溯。
- 错误开场、主持人口播直呼全名和后台话术会在 dry-run 阶段失败。
- 锁定原文仍可包含作者真实姓名，不被误报。
- 显式 `generic` 模式不加载小君君规则。
- 本地回归测试、Python 编译检查和 `quick_validate.py` 全部通过。
- 整个升级验证过程没有调用付费 TTS API。
