# 研报成片编排可靠性升级设计

## 背景与目标

一次“完整视频 + PDF 首屏横版 + 方案三竖版”提交会跨越研报文案、整篇 WAV、视觉分镜、图片、音频对齐、白板视频和 Publisher 成片等多个子流程。当前各流程已有可复用产物和失败续跑能力，但父任务状态、子任务状态与产物可用性仍有耦合，运营人员需要跨页面判断恢复路径。

本设计将人工作业收敛为“选择 PDF 与配置、提交、审阅成片”三步。系统必须自动建立依赖、按产物复用、只重试失败节点、在子任务完成时立即收口，并在横版和全部所选竖版均通过质量门禁后才宣告完成。B站等发布动作继续独立受显式开关控制。

## 范围

本轮按三个可独立验收的里程碑推进：

1. **P0 编排可靠性**：修复等待态容量误计数，补齐子任务完成后的父任务即时唤醒，统一成片完成契约。
2. **P1 运营可见性**：在现有详情页聚合阶段状态、等待原因、队列保护信息、可复用产物和失败节点操作。
3. **P2 统一编排抽象**：把成熟的节点状态、依赖和产物契约抽成通用 DAG/产物注册接口，逐步迁移现有流程。

本轮不重写全部 Celery 工作流，不修改发布权限边界，不删除历史任务或原始审计 JSON，也不引入新的外部基础设施。

## 方案比较

### 方案 A：增量强化现有 PublicationTask 状态机（采用）

沿用现有任务表、结构化投影列、Celery 队列和恢复服务，先修正真实运行状态与守卫规则的偏差，再增加幂等的完成事件唤醒和统一产物验收。

优点是改动面可控、可用现有测试框架验证、能够兼容历史任务；缺点是短期仍保留若干分散的编排函数。

### 方案 B：立即建设全新 DAG 编排器

新建节点、边、产物和事件表，一次迁移全部研报流程。架构最整洁，但需要同时迁移 API、Worker、修复器和前端，运行风险与回滚成本都很高，不适合在当前活跃工作区直接实施。

### 方案 C：只做单页工作台

用界面聚合现有状态并提供重试按钮。交付快，但容量死锁、重复投递、父任务延迟收口和伪完成仍存在，只会把结构性问题隐藏在更友好的界面下，因此不采用为主路线。

## 目标架构

现阶段继续以研报音频父任务为一次提交的业务主键。各节点输出可验证产物，父任务只保存摘要和关联 ID：

`PDF → 文案 → WAV → 分镜 → 图片 → 整篇音频对齐 → 白板视频 → Publisher（横版 + 所选竖版）→ 质量门禁`

核心原则：

- **状态与产物分离**：父任务后置失败不使已经存在且校验通过的文案、WAV、图片或视频失效。
- **依赖前置建立**：完整视频选择方案三时，提交阶段自动写入并创建 `stick_figure` 视觉依赖。
- **幂等续跑**：同一 PDF、配置和节点输入哈希只能有一个有效输出；默认续跑只处理未完成或失败节点。
- **等待态不占运行容量**：父任务把工作交给子任务后属于被动等待，不占用父 Worker 的并发额度。
- **事件优先、轮询兜底**：子任务终态立即唤醒等待父任务；延迟重试与 watchdog 只负责丢事件恢复。
- **完成必须满足契约**：横版和所有所选竖版文件都存在、非空、可解码且时长合理后，父任务才能进入 `completed`。

## 组件设计

### 1. 等待态规范化

`report_audio_workflow._current_step_code()` 会把 `publisher_video_waiting` 压缩为 `pub_waiting`，把其他长步骤压缩为 `gem_*`、`doubao_*`。运行准入守卫必须识别持久化后的实际步骤，而不是只识别压缩前的内部名称。

第一批改造增加实际等待前缀 `pub_`，并为现有 `gem_`、`doubao_` 压缩步骤建立合同测试。只有真正执行父流程的步骤才计入 `report_pdf_audio_workflow` 运行容量。

### 2. 子任务终态即时唤醒

Publisher、视觉视频和其他长耗时子任务写入终态后，调用一个幂等父任务唤醒接口。接口以 `parent_id + child_id + waiting_child_updated_at` 做比较更新，避免同一完成事件重复入队。

唤醒成功后发布一次新的父任务 Celery 消息，并更新父任务的 broker task ID；旧的延迟消息因 task ID 不匹配而安全退出。发布失败时保留可被通用队列修复器识别的状态，watchdog 继续作为兜底。

### 3. 产物级复用

复用判断使用结构化投影与文件完整性：

- 文案：`final_script_chars > 0`，内容字段可读取；
- 音频：WAV 路径存在、字节数大于 0、时长有效，且文案哈希匹配；
- 分镜/图片：分镜哈希匹配，正文图片全部 `completed` 且路径存在；
- 白板视频与 Publisher：任务终态完成，文件存在且通过质量门禁。

父任务为 `failed` 时，只要失败发生在下游且上述产物条件成立，仍允许复用。身份或哈希不匹配时不得因文件名相似而复用。

### 4. 统一完成契约

新增纯函数式产物检查器，输入父任务配置和 Publisher 摘要，输出每个必需产物的 `ready/path/reason`。至少检查：

- 横版启用时 `video_path` 存在、非空；
- 每个 `vertical_video_schemes` 都有对应输出路径；
- MP4 可被媒体探测器读取，含视频流和音频流；
- 时长大于 0，并与最终 WAV 时长在允许误差内；
- B站关闭时不存在自动发布执行记录。

检查失败时父任务保持可恢复状态并展示具体缺失项，不写入伪完成。

### 5. 运营工作台

详情 API 聚合现有结构化投影，不在列表轮询中读取整份大 JSON。前端以一个阶段条展示：输入、文案、音频、视觉、成片、质量门禁、发布。每个阶段显示 `运行中/等待/失败/完成/已复用`、等待原因和最后更新时间。

失败操作只提供“续跑失败节点”和“明确重新生成本节点”。容量保护显示原因、活动数、限制和下次重试时间，避免运营人员将正常排队误判为卡死。

## 数据流与错误处理

提交时先规范化配置并建立依赖，再创建父任务。Worker 每进入一个节点先查找匹配且完整的产物；命中则记录复用来源并跳过外部调用。未命中才创建或复用唯一子任务。

错误分为四类：

- `waiting_dependency`：依赖仍在运行，事件唤醒，轮询兜底；
- `capacity_deferred`：容量保护，展示下一次重试；
- `retryable_failure`：网络、浏览器或瞬时数据库错误，有限自动恢复；
- `human_required`：登录、验证码、配置缺失或内容质量失败，停止自动重试并给出操作说明。

重试不得创建同角色、同输入哈希的重复活动子任务。强制重生成必须产生新的输入版本并保留旧产物审计记录。

## 测试与验收

每项行为先写失败测试，再实现最小改动。第一批至少覆盖：

1. 持久化步骤为 `pub_waiting`、`pub_queued` 时不占父流程运行容量；真正执行步骤仍计入容量。
2. 方案三完整视频提交自动请求 `stick_figure` 视觉工作流。
3. 父任务后置失败但文案与 WAV 完整时，视觉分镜和整篇音频对齐可以复用。
4. 同一 Publisher 完成事件重复到达只唤醒父任务一次。
5. 完成契约缺任一横版/竖版产物时拒绝完成，六个真实 MP4 类型的测试夹具可被正确识别。
6. B站开关关闭时，完整成片不会产生发布任务。

运行验收目标：

- 三份 PDF 同时提交时，等待 Publisher 的父任务不再占据并发上限；第三份无需等待前两份父任务回写后才能启动。
- 子任务完成后父任务在一个事件周期内收口，60/180 秒延迟仅作为丢事件兜底。
- 一次业务提交每种必需成片最多一个有效 Publisher 输出。
- 页面明确区分“等待、失败、已复用、完成”，运营人员无需查询数据库或任务 ID。

## 实施顺序

1. 修复实际等待步骤的容量识别并加入合同测试。
2. 增加幂等子任务终态唤醒，先接 Publisher，再接视觉视频。
3. 抽取统一成片完成契约并接入父任务完成路径。
4. 将状态、等待原因和质量门禁结果投影到详情 API。
5. 更新运营工作台与端到端回归测试。
6. 在上述接口稳定后，再评估独立 DAG/产物表迁移，不提前大规模重写。
