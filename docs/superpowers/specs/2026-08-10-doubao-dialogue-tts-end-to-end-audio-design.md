# 豆包双人研报播客 Skill 模块化升级设计

## 设计结论

升级现有 `doubao-dialogue-tts` Skill，使用户只需提交一份研报或文章，即可完成“小君君精读点评文案 → 人工审稿 → 双声线分段合成 → 完整音频合并 → 收费节点建议”的端到端流程。

本阶段只交付稳定的音频生产能力。视频制作不进入本阶段实现范围，但音频输出必须预留统一时间轴契约，使未来能够继续扩展画面策划、片头、字幕和最终视频渲染，而无需重做文案或语音。

## 2026-08-31 实施补充

- “小君君”已明确为当前频道项目的默认 Profile，不是所有 `doubao-dialogue-tts` 调用的全局默认。
- 项目通过 `.doubao-dialogue-tts.json` 选择 `xiaojunjun-honghao`；通用 Skill 在其他项目保持 generic，可被单期明确覆盖。
- Profile 已固化固定开场、“洪总”口播称呼、粉丝受众关系、解释而非挑错的主持职责、后台话术隔离，以及清澈 `1.08` / 刘飞 `1.00` 的默认语速。
- “API 计费边界”与“内容付费节点”是两个独立概念：前者是获得授权后的第一条真实豆包请求，后者是依据最终节目时间轴选择的免费试听结束位置。

## 已确认的产品原则

1. 对用户保持一个 Skill 入口，不要求用户理解多个内部工具。
2. 在当前频道项目中，用户默认只提供研报，不再重复提交“小君君”人物与栏目提示词。
3. 原文完整度是硬约束：不得删减、压缩、重排或改写原文。
4. 点评位置和数量根据文章逻辑增量决定，不按文章长度或固定数量决定。
5. 小君君是听众的认知向导，兼顾专业与网感，但不能抢占原作者身份。
6. 完整文案必须经过用户确认；确认前不得调用付费语音服务。
7. 文案确认后，再以自然语言询问用户是否发送至豆包并开始付费合成，不要求固定口令。
8. 默认收尾简洁，不口播点赞、订阅、评论或投资建议免责声明：

   > 建议大家关注三件事……
   >
   > 以上就是本期内容，我们下期见。

9. 音频完成后输出最佳收费节点建议，但不额外切割免费版与付费版音频。
10. 视频是后续独立里程碑，需要通过真实样片迭代确认换画节奏、字幕和视觉风格。

## 范围

### 本阶段包含

- 研报原文存档与完整性保护；
- 文章论证结构分析；
- 基于逻辑增量的点评位置判断；
- 小君君栏目文案生成；
- 主持补充信息的实时核验与非口播引用记录；
- 文案审阅、修改与确认；
- 播音规范化及变更记录；
- 双声线分段合成、缓存、续跑和局部重生成；
- MP3/WAV 合并与媒体完整性校验；
- 最佳收费节点及备选节点建议；
- 面向未来视频阶段的统一时间轴输出契约。

### 本阶段不包含

- 自动搜集或生成视频画面；
- 片头视频或片头音频混合；
- 字幕强制对齐与烧录；
- 最终 MP4 渲染；
- 自动切割免费试听版和付费完整版；
- 与当前仓库中既有研报成片后台工作流的直接集成。

## 用户工作流

1. 用户粘贴或上传研报。
2. Skill 保存完全不变的原始输入并分析文章论证结构。
3. Skill 识别值得主持人介入的逻辑节点，检索并核验需要补充的最新信息。
4. Skill 生成完整审阅稿：固定开场、全部原文、小君君点评、简洁收尾。
5. Skill 同时生成独立的发布素材，包括标题、简介、标签和非口播来源记录。
6. Skill 暂停，等待用户修改或确认文案。
7. 用户确认后，Skill 生成播音规范化文本、变更记录和语音 manifest。
8. Skill 明确询问用户是否将文本发送至豆包并开始付费合成。
9. 用户同意后，Skill 先执行 dry run，再生成分段 WAV/MP3，并合并完整节目。
10. Skill 验证全部文件、时长、文本哈希和失败报告。
11. Skill 根据最终音频时间轴输出最佳收费节点建议。
12. Skill 交付完整 MP3、WAV、分段音频、最终文案、变更记录、生成报告和收费节点建议。

## 内部模块

### 1. 栏目与人格模板

将原始长提示词拆为独立的栏目模板资源，不把整段提示词堆入 `SKILL.md`。模板保存以下稳定偏好：

- 主持人名称：小君君；
- 固定开场：`哈喽兄弟们好，欢迎回到我的频道，我是你们的老朋友小君君。`；
- 表达原则：专业是内容骨架，网感是表达方式；
- 人格特征：敏锐、严谨、有江湖气、偶尔调皮，不煽动、不喊单；
- 语言节奏：短句、口语化、信息密度高；
- 主持职责：认知翻译、逻辑拆解、实时核验和人格表达；
- 默认简洁结尾，不口播互动号召或免责声明。

人格不能退化为重复口头禅。主持人不得把原文观点伪装成自己的判断，也不得把新增信息归因给原作者。

### 2. 原文完整性模块

建立三层文本：

1. `source-original.txt`：用户输入的原始文本，完全不改动；
2. `final-script.md`：保留全部原文，只在原文段落之间加入主持内容；
3. 语音 manifest：在不改变语义的前提下进行发音规范化。

允许的编辑仅限于语义确定的少量错别字、断句和播音发音转换。任何可能改变原意的问题不得静默修改，应保留原文并在主持点评或审阅说明中指出。

生成 `normalization-log.json`，逐项记录原始形式、播音形式、原因和对应分段。典型转换包括数字、日期、百分比、货币、英文缩写、符号和视觉专用标记。原始文件永远是审计基线。

### 3. 论证结构与点评节点模块

先构建文章逻辑树，再选择点评节点。候选节点包括：

- 核心命题首次提出；
- 因果链条发生转折；
- 数据与结论之间出现推导跳跃；
- 原文观点需要事实核验或口径限定；
- 一个变量开始影响其他资产；
- 市场共识与原文判断发生冲突；
- 出现足以改变全文结论的新因素。

每个候选节点必须通过“逻辑增量”门槛。主持点评至少提供一种原文没有的新价值：纠正或限定、补充最新事实、解释定价机制、串联分散信息或防止听众误读。

不设固定插入数量，也不以文章篇幅推导数量。相邻且重复的候选节点应合并；不能增加理解价值的候选节点应删除。点评数量是分析结果，不是任务指标。

### 4. 实时核验模块

对主持人新增的时效性数据和高风险财经结论使用权威来源核验。原文作者的观点与主持新增信息必须明确分开。

引用链接和核验说明进入审阅资料，不进入播音文本。无法验证的精确数字应删除、降级为条件判断或明确注明不确定性，不得为增强节目效果而编造细节。

### 5. 审稿状态机

文案生成后进入 `awaiting_script_review`。用户可以要求修改点评、插入位置、语气、开场或结尾。每次修改同步更新 `final-script.md`，但不得开始语音合成。

用户确认文案后进入 `script_approved`，随后生成播音规范化层和 manifest。Skill 再询问是否开始豆包付费合成。只有用户明确同意第三方传输与生成，状态才进入 `synthesis_authorized`。

不依赖固定口令，依据当前对话中的明确意图判断状态。模糊回复不触发付费调用。

### 6. 语音生产模块

继续使用现有成熟能力：

- 主持/点评：清澈声线；
- 原文：刘飞声线；
- 当前频道默认语速：清澈 `1.08`，刘飞 `1.00`，允许单期明确覆盖；
- 逻辑分段与内部 API 切块分离；
- 文本、声线、模型和音频设置哈希匹配时复用已有分段；
- 局部文案修改后只重生成发生变化的分段；
- 生成完整 WAV 和 MP3；
- 使用 `ffmpeg` 与 `ffprobe` 验证可解码性、时长和媒体参数；
- 生成有效 manifest 和无失败项的生成报告后才能宣告完成。

### 7. 收费节点模块

收费节点依据最终音频而不是文字字数决定。评分维度包括：

- 免费部分是否已经交付真实价值；
- 当前句子是否形成自然悬念；
- 后续是否进入全篇最稀缺的逻辑；
- 节点是否位于完整段落或主持点评结尾；
- 节点之后是否仍有足够的付费内容；
- 切换是否损害听感或显得诱导。

输出一个最佳节点和必要时一个备选节点，包含时间戳、前后句、选择理由和可选过渡口播。模块不修改或切割音频文件。

## 输出契约

```text
project/
├── source-original.txt
├── final-script.md
├── publishing-package.md
├── normalization-log.json
├── manifest.json
└── output/
    ├── effective-manifest.json
    ├── generation-report.json
    ├── program-timeline.json
    ├── monetization-note.md
    ├── segments/
    │   ├── 001_*.wav
    │   ├── 001_*.mp3
    │   └── ...
    ├── complete-program.wav
    └── complete-program.mp3
```

`publishing-package.md` 与播音文本分离，包含标题组合、简介、标签、来源链接和可配置的非口播合规说明。

## 视频扩展契约

本阶段只生成 `program-timeline.json`，不生成视频。该文件至少包含：

- 节目总时长与音频参数；
- 每个逻辑分段的 ID、角色、文本、开始和结束时间；
- 原文或点评类型；
- 当前逻辑主题与可选画面提示；
- 收费节点；
- 将来加入片头后的时间偏移字段。

未来视频模块以时间轴为唯一上游接口，继续生成：

1. `visual-plan.json`：画面类型、素材来源、场景边界和转场；
2. 片头包：片头音频、标题画面与品牌元素；
3. 字幕：基于已确认播音文本做强制对齐，不依赖纯语音识别猜测文字；
4. 字幕样式：字体、像素字号、颜色、描边、阴影、行宽、行数、位置与安全区；
5. 最终长视频：片头、主音频、画面、字幕和转场的统一渲染。

长篇财经节目属于可迭代的定制视频流程。第一版成片必须通过真实样片调试确定画面密度、换画节奏、字幕位置、字体尺寸和片头衔接，不能在音频阶段提前锁死这些视觉参数。

## 错误处理

- 原文缺失或无法读取：停止并请求重新提供文件；
- 逻辑节点不清晰：保留原文连续播放，不为满足数量而硬插点评；
- 最新信息无法核验：降低断言强度或删除主持补充；
- 用户修改原文：将其视为用户明确的新版本，并保存版本记录；
- 文案未确认：禁止生成 manifest 的付费执行版本；
- 未明确授权豆包调用：禁止联网合成；
- 个别分段失败：保留成功缓存，只重试失败或过期分段；
- 合并或媒体校验失败：不得交付为成功，保留分段以便恢复；
- 收费节点缺乏自然位置：如实说明不建议设置强制节点，不伪造悬念。

## 验证与验收

### 静态验证

- Skill 元数据和目录结构通过 `quick_validate.py`；
- 栏目模板、原文规则和 TTS 规则不存在互相冲突；
- 原文、审阅稿和语音 manifest 可建立逐段对应；
- `normalization-log.json` 覆盖所有非原样播音转换；
- `program-timeline.json` 结构可被未来视频模块独立消费。

### 行为测试

至少使用以下场景验证：

1. 长文但逻辑单一：插入点应少，不得因篇幅机械增加；
2. 短文但逻辑密集：允许出现多个高价值点评节点；
3. 原文包含错字、数字、英文缩写和图表标记：原始文件不变，播音转换有完整记录；
4. 用户修改结尾：只使对应分段失效，其他语音继续复用；
5. 用户只确认文案但未同意合成：不得调用豆包接口；
6. 一个分段合成失败：报告不得宣告完成，重试不重复生成成功分段；
7. 完整节目生成：分段数量、合并时长、文本哈希和媒体文件全部通过校验；
8. 收费节点：输出时间戳和逻辑理由，不生成拆分音频；
9. 视频扩展模拟：独立消费者仅依赖 `program-timeline.json` 即可还原节目段落和时间范围。

### 成功标准

- 用户只提交研报即可得到符合小君君栏目风格的完整审阅稿；
- 原文内容和顺序得到完整保护；
- 点评数量由逻辑增量自然产生；
- 用户始终能够在付费合成前调整和确认文案；
- 局部修改不会导致全篇重复付费合成；
- 所有交付音频均可解码且报告无失败项；
- 收费节点建议与最终音频时间一致；
- 后续视频功能可以通过时间轴契约接入，而不破坏当前音频流程。

## 实施边界

本设计获批后，下一步只为现有 `doubao-dialogue-tts` Skill 编写实施计划。实施计划应优先完成栏目模板、原文保护、逻辑点评、审稿状态和输出契约，再扩展收费节点与统一时间轴。视频画面、字幕和 MP4 渲染另行立项，待音频阶段稳定并获得真实样片反馈后再设计实施。
