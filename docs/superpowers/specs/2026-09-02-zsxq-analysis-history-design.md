# 知识星球文件分析与历史追溯设计

## 1. 背景与目标

用户会从知识星球导出两类互相独立的列表 JSON：

- `kind=pdf`：PDF 文件清单，重点分析文件热度、主题分布、研究资料结构和上传时间。
- `kind=audio`：音频文件清单，重点分析时长结构、文件热度、主题分布和可优先处理的音频。

两类输入不做合并，不用同一套指标强行比较。页面提供一个入口、两个 Tab；每次上传生成一个不可覆盖的分析批次，并可以在对应 Tab 中回看历史批次。

当前 JSON 只有文件元数据（`fileId`、`topicId`、`name`、`status`、`downloadCount`、`fileSize`、`duration`、`uploadTime` 等），没有 PDF 正文、音频转写文本或本地文件路径。因此第一版分析应明确标注为“清单元数据分析”，不假装已经理解文件正文。

## 2. 已确认的输入契约

顶层对象必须符合：

```json
{
  "schema": "zsxq-list-export/v1",
  "kind": "pdf 或 audio",
  "exportedAt": "ISO 8601 时间",
  "summary": {},
  "items": []
}
```

服务端重新从 `items` 计算所有统计指标，不信任客户端传来的 `summary`。每个 item 按 camelCase 字段读取并规范化为内部列。上传 Tab 的类型必须与 JSON 的 `kind` 一致。

约束：UTF-8 JSON，最大上传体积 5 MiB，最多 5,000 条 item；数值不能为负；`status` 只接受 `done`、`pending`、`failed`、`processing`；同一批次内重复 `fileId` 不会静默合并，会保留原始行并记录重复数量。

## 3. 持久化模型

不在数据库中保存整个输入 JSON 或整个结果 JSON，也不在历史列表接口读取 JSON。原始上传字节以不可变审计文件保存到项目 `data/zsxq_analysis/users/<user_id>/<run_id>.json`，数据库保存相对路径、字节数和 SHA-256。原始文件只在用户明确请求某个批次的“下载原始 JSON”时，经过批次归属校验后读取。

新增四张表：

### `zsxq_analysis_runs`

一行代表一次上传和一次独立分析。保存 `user_id`、`kind`、原始文件名、schema、导出时间、输入 hash、分析版本、处理状态、批次汇总列（条数、状态计数、下载总数、文件大小总量、音频总时长、主题数、重复 fileId 数、数据起止日期）、审计文件相对路径和错误信息。

### `zsxq_analysis_items`

一行代表输入中的一条文件记录。保存批次内索引、file/topic ID、名称、分组、原始上传时间文本、解析后的上传时间、下载次数、文件状态、文件大小、音频时长和重复标记。索引覆盖批次+下载次数、批次+状态、批次+topicId。

### `zsxq_analysis_topics`

一行代表某批次中的一个 `topicId` 聚合。保存文件数、下载总数、最大下载次数、完成数和最近上传时间，避免每次打开详情都重新扫描全部 item。

### `zsxq_analysis_keywords`

一行代表某批次的一条可解释关键词。保存关键词、出现文件数、下载次数总和、排名和提取类别。关键词来自文件名的确定性规则/停用词过滤；不引入外部 NLP 服务，也不把关键词结果塞进 JSON。

所有表均以 `user_id` 归属的 run 为边界。除管理员明确扩展需求外，API 只允许当前用户读写自己的批次。

## 4. API 契约

统一前缀：`/api/v1/zsxq-analysis`，全部接口要求登录。

- `POST /runs`：multipart 上传 `file`，可选 `kind`。解析、规范化、分析、写入四张表，并返回批次详情摘要。
- `GET /runs?kind=pdf|audio&page=1&per_page=20`：只返回窄投影历史列表，不读取审计文件，不返回 item/keyword 明细。
- `GET /runs/<run_id>`：读取一个归属当前用户的批次，返回汇总、关键词、主题聚合和有限数量的代表 item。
- `GET /runs/<run_id>/items?page=1&per_page=50&status=...`：分页读取结构化 item，支持下载次数排序，避免详情接口一次返回全部数据。
- `GET /runs/<run_id>/source`：在归属校验后下载原始 JSON；这是唯一的原始大对象读取路径。

不存在或不属于当前用户的 run 统一返回 404，避免泄露资源是否存在。列表和详情均不跨 PDF/audio 汇总。

## 5. 分析结果设计

### PDF Tab

- 汇总卡：文件数、已下载/待下载、主题数、下载总数、总文件大小、数据日期范围。
- 关键词词云/关键词排行：按文件出现数展示，下载次数作为辅助排序；同一批次内计算，不和音频 Tab 混用。
- 主题排行：按文件数、下载总数和代表文件展示。
- 下载热度排行：展示最受关注的 PDF。
- 上传时间趋势：按日统计文件数量和下载次数。

### 音频 Tab

- 汇总卡：音频数、已下载/待下载、主题数、总时长、平均/中位时长、总下载数。
- 关键词词云/关键词排行：仍按文件名确定性提取，但单独存储在该批次。
- 时长分布：未知（0 秒）、短音频（少于 15 分钟）、中等音频（15 分钟及以上且少于 45 分钟）、长音频（45 分钟及以上）。
- 热度与处理优先级：按下载次数降序；并展示时长和状态，不把下载次数解释为内容质量。
- 上传时间趋势：按日统计数量和总时长。

## 6. 事务、隔离和性能边界

1. 上传体积检查、字节 hash、JSON 解析、规范化和分析在不持有数据库连接时完成。
2. 原始审计文件使用批次 UUID 命名并原子写入；DB 事务失败时尽力删除刚写入的孤儿文件。
3. 一次 DB 短事务批量插入 run/items/topics/keywords；不逐行提交。
4. 历史列表使用显式结构化列投影和 `user_id + kind + created_at` 索引，不读取原始文件、不读取结果 JSON。
5. 明细接口只按主键读取一个 run，再用分页 SQL 查询子表；不依赖 ORM relationship 自动加载全部内容。
6. 该版本不启动 Celery：317 条级别的元数据分析是同步、可控且可回滚的；未来若加入正文抽取/转写，另建异步分析版本和 artifact，不改变当前历史批次模型。

## 7. 不在本期范围

- 不把 PDF 正文、音频转写、AI 摘要混入当前清单分析。
- 不将 PDF 和 audio 的 item、关键词或趋势合并成一张总榜。
- 不通过读取已有 `zsxq_topics` / `zsxq_attachments` 大对象来猜测上传 JSON 的内容。
- 不用浏览器 localStorage 代替数据库历史。
