## 2. 2026-08-18 暴露的问题

侧边栏执行 MP3 下载后出现了三类同时发生的问题：

1. 已经下载并进入过系统的 MP3 又被下载，Downloads 中出现 Chrome 自动添加的 `(1)`、`(2)` 等副本。
2. 同一轮中存在重复下载，且报告中的“新下载数量”与实际 manifest 文件数量不一致。
3. manifest 声明的 `filename` 与 `absolute_path` 实际文件名不匹配，首次提交失败；侧边栏随后修改 manifest 却继续使用同一个 run_id，于是触发“同一 run_id 已提交不同 manifest”的幂等冲突。

PDF 同期也出现了同类 manifest 路径/文件名校验失败和 run_id 冲突，只是重复下载证据在 MP3 上最明显。

## 3. 已确认的根因

### 3.1 历史去重键不稳定

旧逻辑把原始发布时间字符串和 `source_url` 放入身份键。同一个文件会因为以下差异被当成不同文件：

- `2026-08-17T13:39+08:00`
- `2026-08-17T13:39:00+08:00`
- 同一标签页 URL 的中文、百分号编码或其他序列化差异
- Chrome 自动生成的 `文件名 (1).mp3`

因此“历史中已经有这个文件”并不一定能命中。

### 3.2 失败 manifest 被错误当作可信历史

旧历史服务扫描 inbox 中所有 `sidebar-submit-*.json`。即使 manifest 在后端校验阶段失败、从未产生 `ZsxqBrowserSubmission` 数据库接收凭证，它仍会被下一轮历史接口读到。这既可能掩盖真正未入库的文件，也可能放大错误绑定。

### 3.3 候选、弹层和真实下载文件没有形成一一绑定

知识星球详情弹层和浏览器下载完成事件都可能异步到达。旧 skill 可能出现：

- 打开的是候选 A，但弹层仍显示上一个候选 B；
- 下载按钮或下载次数第一次尚未加载，就立即被判定为缺失；
- 点击 A 后未等待 A 的确定完成事件，就开始处理 B；
- 之后通过“最近新增文件”推测路径，把较晚完成的文件绑定到错误候选。

实际事故中，真正的“中信-周一九点半…”文件约在 08:52 才完成，但错误 manifest 已在约 08:33 把另一条候选与 `再看潍柴... (2).mp3` 绑定。这证明仅看目录最新文件无法保证正确性。

### 3.4 同轮缺少实际文件集合

旧 skill 没有维护规范化后的实际落盘文件名集合，Chrome `(1)` 副本可以再次进入同一个 manifest。

### 3.5 最终报告没有强制来源于冻结 manifest

扫描过程中的临时计数、点击次数和最终 manifest 可以各自变化，导致报告称下载 N 个，但实际 `files` 长度不同。提交后再修改 manifest，又破坏了 run_id 幂等约束。
