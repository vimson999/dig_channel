## 3. 已确认的根因

### 3.1 历史去重键不稳定

旧逻辑把原始发布时间字符串和 `source_url` 放入身份键。同一个文件会因为以下差异被当成不同文件：

- `2026-08-17T13:39+08:00`
- `2026-08-17T13:39:00+08:00`
- 同一标签页 URL 的中文、百分号编码或其他序列化差异
- Chrome 自动生成的 `文件名 (1).mp3`

因此“历史中已经有这个文件”并不一定能命中。

### 3.2 失败 manifest 被错误当作可信历史

旧历史服务扫描 inbox 中所有 `sidebar-submit-*.json`。即使 manifest 在后端校验阶段失败、从未产生 `ZsxqBrowserSubmission` 数据库接收凭证，它仍会被下一轮历史接口读到。这既可能掩盖真正未入库的文件，也可能放大错误绑定。

### 3.3 候选、弹层和真实下载文件没有形成一一绑定

知识星球详情弹层和浏览器下载完成事件都可能异步到达。旧 skill 可能出现：

- 打开的是候选 A，但弹层仍显示上一个候选 B；
- 下载按钮或下载次数第一次尚未加载，就立即被判定为缺失；
- 点击 A 后未等待 A 的确定完成事件，就开始处理 B；
- 之后通过“最近新增文件”推测路径，把较晚完成的文件绑定到错误候选。

实际事故中，真正的“中信-周一九点半…”文件约在 08:52 才完成，但错误 manifest 已在约 08:33 把另一条候选与 `再看潍柴... (2).mp3` 绑定。这证明仅看目录最新文件无法保证正确性。

### 3.4 同轮缺少实际文件集合

旧 skill 没有维护规范化后的实际落盘文件名集合，Chrome `(1)` 副本可以再次进入同一个 manifest。

### 3.5 最终报告没有强制来源于冻结 manifest

扫描过程中的临时计数、点击次数和最终 manifest 可以各自变化，导致报告称下载 N 个，但实际 `files` 长度不同。提交后再修改 manifest，又破坏了 run_id 幂等约束。

### 3.6 “单下载在途”的自然语言约束不是事务

第一版修复虽然写了“同时只能有 1 个下载任务在途”和“无法绑定就停止”，但仍缺少以下不可绕过的运行态：

- 点击前创建的唯一账本项；
- 下载完成监听器必须先进入 active，再允许点击；
- 每次点击与唯一终态事件的数量核对；
- 无 armed 候选的意外事件、连接重置和未决点击触发不可清除的 `abort_latch`；
- “停止继续下载”与“因文件污染禁止提交 manifest”两个独立状态。

因此执行代理可以合理化为“未确认项不计成功，继续处理下一个候选”，或在连接恢复后继续点击。这正是 Gate A 的 MP3/PDF 现场行为。

### 3.7 点击后缺少路径/文件名被错误降级为可继续失败

正式 MP3 轮次揭示了第二层根因：浏览器已经返回 17 个完成终态并实际写入 17 个文件，但完成结果没有提供 `absolute_path` 和 `filename`。旧规则把 `download_result_incomplete_after_retry` 归类为“候选级失败”，关闭当前候选后继续点击；同时还允许提交 `files: []`。这导致：

- 已落盘文件没有进入 manifest、可信历史、清洗和发布；
- 下一轮仍会把这些文件视为新候选；
- 已存在旧游离文件时，Chrome 直接生成 `(1)` 副本；
- 一次下载元数据能力故障被放大成 17 个游离文件。

进一步复盘后的最终边界不再把“停止后续点击”与“禁止提交已确认文件”绑在一起：点击前失败、明确 `download_failed` 且未落盘，以及已获得唯一终态但真实文件错配/同轮重复的单候选失败，都记录后跳过当前候选并继续。终态超时、缺路径/文件名、当前候选内可隔离的事件冲突也只隔离当前候选并继续；只有事件跨候选、无 armed 候选事件、迟到事件、在途连接重置或其他全局污染才设置 `abort_latch=true` 并停止本轮后续点击。无论哪种情况，当前未决候选从 `files` 排除后，此前已确认文件仍必须提交。`manifest_blocked_by_download_integrity=true` 只保留给准备提交的 `files` 本身无法通过路径、文件名、同轮重复或内容重复自检的情况。第一次点击前仍必须证明当前下载完成机制能返回非空路径和文件名；不能用真实下载试探能力。

### 3.8 下载对象能力预检把“无直接字段”误判为“无路径能力”

2026-08-19 08:41 的 PDF 复验揭示了能力预检本身的问题：Chrome 的 `waitForEvent("download")` 返回 `PlaywrightDownload`，公开渲染可能显示为空对象，但同一对象实际提供异步 `download.path()`。旧 skill 要求事件对象直接同时出现 `absolute_path` 与 `filename`，所以在任何点击之前就误判能力不可用。

修复后的适配契约是：点击前先建立唯一 `waitForEvent("download")` promise；点击后等待同一下载对象，调用 `absolute_path = await download.path()`，再用 `filename = basename(absolute_path)` 取得真实落盘文件名。`path()` 返回空值时，固定等待 2 秒后只对同一对象重读一次；仍为空则隔离当前候选并恢复监听代次后继续下一个，禁止扫描 Downloads 猜路径；若出现跨候选/全局污染才停止后续点击，但无论哪种情况都保留并提交此前已确认文件。

### 3.9 一个长浏览器调用处理多个候选，连接重置后仍可继续产生副作用

2026-08-19 09:28 的 MP3 正式复验暴露了第三层边界：虽然 skill 已要求“严格串行、同时只有一个下载在途”，但没有明确禁止在同一次长时间浏览器工具/JavaScript 调用中循环处理多个候选。控制连接重置时，会话无法继续收取完成回执并报告硬中止，但已经发出的长调用仍可能在浏览器侧继续运行和点击。

文件系统证据显示，本轮 09:35:08～09:46:14 实际新增 22 个 MP3；侧边栏只确认前 8 个，最后一个确认文件落盘于 09:42:37，随后还有 14 个于 09:43:38～09:46:14 继续落盘。22 个文件 SHA-256 互不重复，在完整可信三日历史中规范化文件名命中 0/22、内容 SHA 命中 0/22，因此这次不是已经入库文件被重复下载，而是报告漏记了连接失控后的真实下载副作用。

修复后的强约束是：一次浏览器工具调用最多只允许处理一个候选的完整下载事务；禁止在同一 `js`/浏览器调用里用循环、批处理或递归下载多个候选。每个候选完成后必须先返回会话，核对账本终态为 `IDLE`、无未决事务且 `abort_latch=false`，才能发起下一个候选的独立浏览器调用。这样连接中断至多污染当前一个候选，不再让不可见的长批次继续点击。

### 3.10 审计计数没有绑定权威来源

2026-08-19 10:46 的 MP3 正式复验证明下载事务和下游链路已经可以保持 2/2 平衡，但冻结 manifest 的审计字段仍可自相矛盾：`candidate_failures` 明确包含 2 条 `detail_file_mismatch_after_2s`，`scan_summary.detail_file_mismatch_after_2s` 却为 0；历史字段又被写成 106 条记录、106 个唯一文件、折叠重复 0，形态上等同于把 `data.files.length` 同时当成记录数和唯一数。当前可信历史在本轮提交后实际为 209 条记录、108 个唯一文件、折叠 101 条。

根因是 skill 只列出了汇报字段，没有强制失败计数从最终 `candidate_failures` 数组派生，也没有强制历史四项逐字段复制历史页 `data.summary`；后端只校验了 `new_download_success == files.length`，因此错误审计值仍能被接收。

修复后的契约是：`candidate_failure_count == candidate_failures.length`，每个失败阶段计数严格等于数组中同名 `failure_stage` 的条目数；历史 `records_seen`、`unique_downloads`、`duplicates_collapsed`、`ignored_untrusted_manifests` 在首次下载前逐字段冻结，不得从 `data.files.length` 重算。后端现会在持久化和排队前拒绝失败计数不一致的 manifest。

### 3.11 `download.path()` 等待完整落盘超过外层 90 秒，运行时先被重置

2026-08-19 13:47 的 MP3 正式复验提供了确定的运行时证据。第 41 个候选 `重视银行科技叙事260818.mp3` 于 14:01:17 开始处理，候选浏览器调用设置 `timeout_ms=90000`；14:02:47 外层先返回 `js execution timed out; kernel reset, rerun your request`。该 51.5 MB 文件直到 14:03:12 才完成落盘，约耗时 115 秒，所以重置发生时点击已经发出，但 `download.path()` 尚未把真实路径返回账本。

这不是历史去重再次失效，也不是“一候选一调用”屏障失效。可信三日历史对两个实际文件均未命中；屏障把污染范围限制在当前一个在途候选。真正缺陷是旧契约只给下载事件 60 秒、外层工具 90 秒，却没有把会等待完整文件落盘的 `download.path()` 纳入一个短于外层工具的受控内层期限。

修复后的 MP3/PDF 共用契约为：单候选事务 `download_transaction_deadline_ms = 180000`，候选浏览器工具 `browser_tool_timeout_ms >= 210000`；下载事件与 `download.path()` 都通过 `Promise.race` 受内层期限约束。内层先到时必须在外层仍存活时隔离未决候选、冻结已确认 `files` 并正常返回 Gate R，禁止让外层先触发 `kernel reset`；返回后照常提交已确认文件。
