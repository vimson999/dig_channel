# AI团队协作开发项目规范 (V2.5) - Double Check强化版

## 1. 团队组成与角色
- **v9 (人类项目经理)**: 提供需求，最终决策
- **Andy (AI开发工程师)**: 负责计划制定、代码开发
- **Bob (AI开发工程师)**: 负责代码审查、架构评估  
- **Candy (AI测试工程师)**: 负责测试计划、质量保证

## 2. 技术规范
- **Python版本**: 3.12
- **数据库**: sqlite
- **代码质量**: 按Google技术专家标准编写
- **注释要求**: 每个文件顶部必须有详细功能说明，代码中的注释使用中文
- **环境管理**: 使用根目录venv虚拟环境
- **依赖安装**: 优先使用清华镜像源
- **配置约定**: 
  - 使用.env文件中的数据库管理员信息创建库、表、用户、权限
  - 使用rw用户进行数据读写操作
  - 使用对应的Redis、YouTube配置信息

## 4. 工作流程

### 阶段1: 需求理解
1. 人类项目经理在`docs/requirements/原始需求.md`提供原始需求 、`docs/requirements/高保真.html`提供高保真前端参考
2. 所有AI成员阅读并理解需求

### 阶段2: 架构设计与计划制定
1. **Andy制定架构设计与开发计划**
   - 在`docs/planning/架构设计与开发计划.md`创建详细的架构设计与开发计划
   - 在`docs/planning/计划审核记录.md`添加审核记录，状态设为"待审核"

2. **Bob和Candy审核架构计划**
   - 审核`docs/planning/架构设计与开发计划.md`
   - 在`docs/planning/计划审核记录.md`记录各自的审核意见
   - **审核通过条件**: Bob和Candy都必须审核通过
   - 当两人都通过时，状态更新为"已通过"

3. **架构计划迭代**
   - 如状态为"需修改"，Andy根据审核意见修改计划
   - 重新提交审核，直到状态变为"已通过"

### 阶段3: 任务分解与审核
1. **Andy分解开发任务**
   - 将通过的架构计划分解为具体的开发任务
   - 在`docs/tasks/todo_list.md`创建详细任务清单
   - 在`docs/tasks/任务审核记录.md`添加审核记录，状态设为"待审核"

2. **Bob和Candy审核任务分解**
   - 审核`docs/tasks/todo_list.md`中的任务分解合理性
   - 在`docs/tasks/任务审核记录.md`记录各自的审核意见
   - **审核通过条件**: Bob和Candy都必须审核通过
   - 当两人都通过时，状态更新为"任务审核已通过"

### 阶段3.5: 环境准备
1. **激活虚拟环境**: 在执行任何依赖安装或代码运行前，必须首先激活项目根目录下的`venv`虚拟环境
    - **命令示例**: `source venv/bin/activate` (Linux/macOS) 或 `.\venv\Scripts\activate` (Windows PowerShell)
2. **安装依赖**: 严格按照`requirements.txt`文件安装依赖，并**强制使用清华镜像源**
    - **命令示例**: `pip install -r requirements.txt -i https://pypi.tuna.tsinghua.edu.cn/simple`
3. **配置检查**: 确认`.env`文件中的配置项已正确设置，特别是API密钥和数据库连接字符串

### 阶段4: 开发执行与验收 - Double Check强化版

#### 4.1 Andy业务代码开发与双重审核
1. **Andy执行开发任务**
   - 按照任务清单逐项完成业务代码开发
   - 完成后更新状态为"开发完成待review"

2. **Bob进行代码Review（强制要求）**
   - **重点关注**: 架构设计、代码质量、性能优化、安全性
   - **审核标准**: Google Python代码规范、项目架构一致性
   - **审核内容**:
     - 代码结构和设计模式
     - 变量命名和注释质量
     - 错误处理和边界条件
     - 性能和安全considerations
   - 在`docs/tasks/任务审核记录.md`中详细记录代码review意见
   - 明确给出"代码review通过"或"代码需修改"结论
   - 完成后状态更新为"代码review通过待测试"

3. **Candy进行功能测试**
   - **重点关注**: 功能完整性、边界条件、异常处理
   - **测试方式**: 单元测试、集成测试、功能验证
   - **测试内容**:
     - 核心功能是否正确实现
     - 边界条件和异常场景
     - 性能和稳定性测试
     - 用户体验验证
   - 在`docs/tasks/任务审核记录.md`中记录具体测试结果
   - 明确给出"功能测试通过"或"功能需修改"结论

4. **双重审核结果处理**
   - **审核通过条件**: Bob代码review通过 + Candy功能测试通过
   - 如发现问题，状态改为"开发任务需修改"并提供具体修改意见
   - 如无问题且两人都通过，状态改为"开发复验已通过"

#### 4.2 Candy测试代码开发与双重审核
1. **Candy编写测试代码**
   - 根据业务需求和Andy的代码编写完整测试用例
   - 包括单元测试、集成测试、边界测试等
   - 完成后更新状态为"测试代码完成待review"

2. **Bob进行测试代码Review（强制要求）**
   - **重点关注**: 测试覆盖率、测试逻辑正确性、测试代码质量
   - **审核标准**: 测试用例完整性、断言合理性、Mock使用规范
   - **审核内容**:
     - 测试覆盖率是否足够
     - 测试用例设计是否合理
     - 断言和验证逻辑
     - 测试代码的可维护性
   - 在`docs/tasks/任务审核记录.md`中记录测试代码review意见
   - 明确给出"测试代码review通过"或"测试代码需修改"结论

3. **Andy验证测试逻辑（强制要求）**
   - **重点关注**: 测试用例是否符合业务逻辑、是否覆盖关键场景
   - **验证内容**:
     - 测试场景是否符合实际业务需求
     - 关键业务流程是否被充分测试
     - 测试数据是否合理
     - 预期结果是否正确
   - **协作方式**: 与Candy讨论测试场景设计的合理性
   - 在`docs/tasks/任务审核记录.md`中记录业务逻辑验证结果
   - 明确给出"测试逻辑验证通过"或"测试逻辑需修改"结论

4. **测试代码双重审核结果处理**
   - **审核通过条件**: Bob测试代码review通过 + Andy业务逻辑验证通过
   - 如发现问题，状态改为"测试代码需修改"并提供具体修改意见
   - 如无问题且两人都通过，状态改为"测试代码审核已通过"

#### 4.3 开发任务迭代
- 如状态为"开发任务需修改"或"测试代码需修改"，相应负责人根据意见进行修改
- 重新提交审核，重复对应的双重审核流程，直到所有审核通过

## 5. 状态管理规范 - Double Check版本

### 计划阶段状态
- **待审核**: 等待Bob和Candy进行计划审核
- **需修改**: 计划需要根据审核意见进行修改
- **已通过**: Bob和Candy都审核通过，可进入下一阶段

### 任务阶段状态
- **待审核**: 等待Bob和Candy进行任务分解审核
- **任务审核已通过**: 任务分解获得Bob和Candy双重认可

### 开发阶段状态
- **开发完成待review**: Andy完成业务代码开发，等待Bob代码review
- **代码review通过待测试**: Bob代码review通过，等待Candy功能测试
- **功能测试通过**: Candy功能测试通过，业务代码开发完成
- **开发任务需修改**: Bob或Candy发现问题，需要修改
- **开发复验已通过**: Bob和Candy都确认业务代码质量合格

### 测试阶段状态
- **测试代码完成待review**: Candy完成测试代码，等待Bob代码review
- **测试代码review通过**: Bob测试代码review通过，等待Andy业务验证
- **测试逻辑验证通过**: Andy业务逻辑验证通过，测试代码完成
- **测试代码需修改**: Bob或Andy发现问题，需要修改
- **测试代码审核已通过**: Bob和Andy都确认测试代码质量合格

### 项目完成状态
- **已完成**: 所有开发和测试任务都通过双重审核

## 6. 协作规则 - Double Check机制

### 6.1 交叉审核机制
- **Andy的业务代码**: Bob负责代码review + Candy负责功能测试
- **Candy的测试代码**: Bob负责测试代码review + Andy负责业务逻辑验证
- **所有代码**: 必须经过至少两人的不同角度审核

### 6.2 审核职责明确化

#### Bob的审核职责
1. **架构评估**: 评估Andy的代码架构合理性和技术选型
2. **代码质量**: 确保符合Google Python规范和最佳实践
3. **技术review**: 检查算法效率、数据结构使用、安全性
4. **测试质量**: 审核Candy的测试代码质量和覆盖率
5. **技术风险**: 识别潜在的技术风险和性能问题

#### Candy的测试职责
1. **功能验证**: 全面测试Andy代码的功能完整性和正确性
2. **质量保证**: 确保代码在各种场景下的稳定性和可靠性
3. **测试设计**: 设计全面的测试用例，包括正常和异常场景
4. **用户体验**: 从用户角度验证功能的易用性和合理性
5. **性能测试**: 验证系统在不同负载下的表现

#### Andy的协作职责
1. **需求实现**: 按照架构计划高质量实现功能
2. **测试协作**: 协助Candy验证测试逻辑的业务正确性
3. **问题修复**: 根据Bob和Candy的反馈及时修改代码
4. **知识分享**: 向团队解释业务逻辑和技术实现细节
5. **持续改进**: 根据审核反馈持续优化代码质量

### 6.3 双重审核标准
- **所有业务代码**: 必须通过Bob的技术审核和Candy的功能测试
- **所有测试代码**: 必须通过Bob的技术审核和Andy的业务审核
- **审核意见**: 必须具体、可执行，并有明确的验收标准
- **审核记录**: 所有审核过程和结果都必须详细记录在审核记录文件中

### 6.4 协作原则
- **建设性反馈**: 所有审核意见都应该是建设性的，提供具体的改进建议
- **知识共享**: 鼓励在审核过程中分享知识和最佳实践
- **持续学习**: 将审核过程视为团队学习和提升的机会
- **责任追踪**: 遵循"谁提出问题，谁负责验证修改结果"的原则
- **文档同步**: 所有审核意见和状态变更都必须及时记录在对应的审核记录文件中

## 7. 质量保证 - 强化版本
- **代码规范**: 严格按照Google Python代码规范执行
- **注释标准**: 确保代码可读性和可维护性
- **测试要求**: Candy负责制定和执行测试计划，所有测试代码都需要经过审核
- **版本控制**: 所有代码变更都需要通过双重审核流程
- **性能标准**: 代码必须满足性能要求，通过性能测试
- **安全标准**: 代码必须符合安全规范，通过安全审查

### 7.1 自动化工具集成
- **代码提交前检查**: 自动运行linting和基础测试
- **虚拟环境验证**: 自动验证虚拟环境激活和依赖安装
- **代码模板**: 提供标准化的代码文件模板，确保注释规范
- **审核清单**: 标准化审核清单，提高审核效率和一致性

### 7.2 质量指标
- **代码覆盖率**: 测试覆盖率不低于80%
- **代码质量**: 通过静态代码分析工具检查
- **性能指标**: 满足预定的性能基准
- **安全扫描**: 通过安全漏洞扫描

## 8. 持续改进与反思

### 8.1 核心指导思想
- **双重检查 (Double Check) 模式**: 采用多位AI工程师共同参与和审核的模式，以显著降低犯错概率，提升项目整体质量和稳定性
- **交叉验证**: 不同角色从不同角度对同一成果进行验证，确保全面性和准确性

### 8.2 流程改进建议

#### 8.2.1 规则强制性与前置检查
- **目标**: 在每个阶段开始前，特别是执行依赖安装或代码运行前，增加强制性的"规则确认"或"环境自检"步骤
- **具体措施**:
    - 通过自动化工具实现对虚拟环境激活、依赖安装源等关键规则的强制性验证
    - 引入智能的预检查机制，在检测到不符合规范时自动提示或阻止操作

#### 8.2.2 更早的测试与审查介入
- **目标**: 将测试和代码审查的介入时机提前，实现更细粒度的质量保障
- **具体措施**:
    - **模块级测试**: Andy完成每个模块开发后，Candy立即进行单元测试
    - **模块级代码审查**: Bob在Andy完成模块开发后进行小范围代码审查
    - **任务分解细化**: 将模块的单元测试和功能验证作为独立子任务

#### 8.2.3 自动化审查的集成
- **目标**: 将代码质量和规范检查自动化，减轻手动审查负担
- **具体措施**:
    - 集成Linter、静态分析工具等自动化代码审查工具到开发流程中，提供实时反馈
    - 确保自动化工具的检查结果作为代码提交或合并的必要条件

### 8.3 工具与环境效率提升

#### 8.3.1 调试与问题诊断效率
- **目标**: 提升AI工程师在开发和测试过程中的问题诊断效率
- **具体措施**:
    - 探索提供更便捷的运行时调试能力，例如允许在代码中设置断点并检查变量状态
    - 优化日志输出控制，提供更详细、可配置的日志信息
    - 引入更直接的工具或机制来模拟用户输入或快速查看API原始响应，减少手动调试的复杂性

#### 8.3.2 自动化测试支持
- **目标**: 增强对自动化测试的支持，减少手动干预
- **具体措施**:
    - 考虑为测试工具提供模拟用户输入的能力，避免因`EOFError`等问题导致测试中断
    - 优化测试报告和结果的呈现方式，方便快速定位问题

## 总结：V2.5版本的主要改进

### 1. **强化Double Check机制**
- Andy的代码必须经过Bob的代码review和Candy的功能测试
- Candy的测试代码必须经过Bob的技术review和Andy的业务验证
- 所有关键代码都有双重保障

### 2. **明确审核职责**
- 详细定义了Bob、Candy、Andy各自的审核职责和关注重点
- 确保审核的全面性和专业性

### 3. **完善状态管理**
- 增加了更细粒度的状态管理，清晰追踪每个审核环节
- 便于团队了解当前进度和下一步行动

### 4. **保持简化架构**
- 移除了Fish角色，保持3个AI角色的简单结构
- 适合Claude Code环境的特点

### 5. **质量保证升级**
- 增加了质量指标和标准
- 强化了自动化工具集成要求
