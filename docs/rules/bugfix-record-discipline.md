# Bug 修复记录纪律

本文档约定项目内所有 bug 修复必须同步沉淀 Markdown 记录。目标不是写流水账，而是把已经付过代价的经验变成可复用的工程资产。

## 适用范围

满足任一条件的修复都必须记录：

- 线上或本地真实复现的业务 bug。
- 数据库、队列、worker、调度器、浏览器自动化、外部平台交互相关 bug。
- 用户可见的结果错误、状态错误、误报成功、任务卡死、重复执行、资源泄漏。
- 修复中形成了新的架构经验、运行经验、排障方法或测试策略。

以下情况可以不单独记录：

- 纯文案、样式、按钮间距等无业务风险的小改。
- 明确的一次性调试代码清理。
- 已被同一 bug 记录覆盖的后续机械补丁。

## 存放位置

- bug 记录目录：`docs/bugs/`
- 索引与模板：`docs/bugs/README.md`
- 文件命名：`YYYY-MM-DD-短英文主题.md`

示例：

```text
docs/bugs/2026-06-23-report-audio-detached-session.md
```

## 必填内容

每条 bug 记录必须包含：

- 基本信息：日期、状态、影响模块、严重级别。
- 现象：用户看到什么、日志报什么、任务处于什么状态。
- 影响：影响哪些业务结果，是否会误报成功、重复执行、丢数据或阻塞队列。
- 根因：代码层和架构层原因都要写清楚。
- 解决思路：为什么选这个方案，排除了什么风险。
- 实际方案：改了哪些模块，核心策略是什么。
- 验证方式：跑了哪些测试、查了哪些任务、确认了哪些结果。
- 复发预防：新增测试、监控、日志、项目标准或后续改造项。

## 修复流程要求

1. 先确认 bug 是否真实存在，不能只按猜测修。
2. 修复前尽量定位最小根因，避免用大范围重构掩盖问题。
3. 修复时补上能防复发的测试或可观测性。
4. 修复完成后补充或更新 `docs/bugs/*.md`。
5. 如果 bug 暴露出通用工程纪律，要同步更新 `docs/rules/`、运行手册或编排标准。
6. 如果 bug 暴露出“已有成熟实现未复用”，必须同步执行 [成功经验复用纪律](reuse-proven-patterns-discipline.md)，检查同类功能是否也漏掉了同一类重试、幂等、续跑、监控或通知机制。
7. 最终提交说明里必须提到对应 bug 记录文件。

## 不合格记录

以下记录不合格，需要返工：

- 只写“已修复”，没有根因。
- 只写代码改动，没有用户现象和业务影响。
- 没有验证项。
- 没有复发预防。
- 把多个无关 bug 混在一个文件里，导致后续难以检索。
