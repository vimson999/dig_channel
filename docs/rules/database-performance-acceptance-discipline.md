# 数据库性能修复验收纪律

## 完成状态

数据库性能改动必须使用以下六级状态，不得跨级，也不得把相邻阶段合并描述：

1. **已定位**：有具体 SQL 指纹、调用路径和运行证据。
2. **代码已修改**：实现和测试通过，但运行进程尚未加载。
3. **迁移已准备**：结构、回填、权限、索引和验证脚本已完成，但尚未在目标库提交。
4. **迁移已应用**：目标库结构、历史回填、权限和索引验证全部通过。
5. **运行进程已替换**：相关 Web、worker、watchdog 和 scheduler 均在明确部署边界后启动。
6. **已解决**：新进程承接真实业务负载并达到验收指标，且业务结果完整。

单测通过、索引存在、SQL 执行计划正常，都不能单独作为“已解决”的依据。

每个 P0 复发簇必须在 `docs/bugs/recurrence-registry.json` 记录机器可校验的 `acceptance_stage`、`last_reopened_at` 和 `blocking_records`。阶段未到 `accepted` 或阻塞项非空时，任何文档、对话或日报都不得使用“已解决”。

## 必备证据

- 修复前基线：时间窗口、SQL 指纹、次数、平均值、P95、最大值和业务场景。
- 代码路径：API/worker/scheduler、函数名和触发频率。
- 部署边界：进程 PID、启动时间、加载的服务角色。
- 修复后样本：同一业务场景至少 5 次；低频任务需覆盖一次完整成功流程。
- 异步工作流的修复后样本必须同时覆盖任务主体和完成后消费者窗口；空闲期或仅看到主任务完成不能代表收尾链路已通过。
- 完整性：状态、产物、通知、重试、取消和历史数据行为不得因性能优化缺失。
- 残余问题：尚未覆盖的进程、SQL 或场景必须明确列为未完成。

## 禁止做法

- 只看代码 diff 或单测就宣布性能问题解决。
- 修改 worker 代码后不重启 worker，却用旧进程日志评价新代码。
- 把重复日志条数直接当作数据库真实执行次数。
- 只加索引，不确认查询形状、返回列、网络载荷和执行计划。
- 为了减列直接删除业务响应字段，或让缓存成为唯一事实来源。
- 在没有真实负载时使用“彻底解决”“已经消失”等结论。
- 在应用连接仍在线时执行 `ALTER TABLE`、普通 `CREATE INDEX` 或大规模回填；等待中的 DDL 排他锁会把后续轻量查询一起阻塞。
- 同一复发键换了 API、worker 或 watchdog 入口后重新按“首次问题”处理。

## 复发升级纪律

- 同一复发键第二次出现时，禁止只修现场函数。必须枚举所有 API、service、worker、scheduler、watchdog 和兼容入口，并明确唯一能力所有者。
- 同一稳定业务实体第二次从 JSON 中过滤、关联、轮询、去重或恢复时，必须拆为结构化列、一对一扩展表或关系表；JSON 只保留审计和冷详情。
- 同一 ORM 过期或 deferred refresh 机制第二次出现时，必须增加完整调用链的实际 SQL 采集测试；源码字符串检查不算验收。
- 同一问题第三次出现时，原 Bug 记录必须重新打开，registry 增加阻塞项，并在真实验收前保持 P0。不得新开临时补丁来重置次数。
- 能力级测试必须同时断言 SQL 条数、所选列、事务提交后的隐式查询和业务响应完整性。

## 热路径设计

- 列表、轮询、watchdog 和关联查询只读取结构化投影列。
- 大 JSON 仅用于冷数据、审计或低频详情，不参与高频过滤和排序。
- 状态更新优先使用结构化列或数据库端原子更新，避免 SELECT-before-UPDATE。
- 进度回调只更新 `current_step/progress` 等结构化状态。累积日志保存在进程内并于终态一次写入，或写入专用事件表；禁止每个进度事件重写 `params/result`。
- 可变日志、事件、子任务和产物数量持续增长时，应拆为专用子表。
- 进程内缓存只能减少重复读取；数据库仍是事实来源，写入必须具备原子性和失败处理。
- 延迟续跑、重试和父子轮询消息必须携带完成当前判断所需的最小结构化快照；禁止只传父任务 ID，再在每一轮重新读取父子完整 JSON。
- 延迟消息必须携带代次/版本令牌，并以 compare-and-set 淘汰重启积压或重复投递的旧消息；旧消息不得继续派生下一轮消息。
- 等待中的轮次只读父子状态投影。完整子任务结果只能在终态收口时读取一次；恢复磁盘产物或修复 stale 子任务属于明确例外，必须有低频门槛和契约测试。
- ORM 实体或实体列表不得跨越 `commit/rollback` 后继续使用。循环内需要提交时，候选必须先转成不可变 `Row`、字典或 DTO；“下一条尚未访问”不代表它不会被 commit 过期。
- 大 JSON 使用延迟物化：先以结构化列完成过滤、判型和复用判断，只对最终需要冷数据的单行按主键读取一次载荷。
- 任务创建后需要返回完整请求/结果时，响应快照必须在 flush 后、commit 前构造；commit 后只能传标量 ID、执行定向 UPDATE 或显式轻量投影，不得再次调用宽实体 `to_dict()`。
- 进度 JSON 必须定义写入预算和终态强制落盘协议。过程心跳用结构化列，完整审计 JSON 可按时间窗口低频持久化；成功、失败、重试边界和跨工作流交接必须强制写入完整最新值。
- 完成阶段的消费者扇出必须声明消息体预算和启动错峰。多个消费者需要同一大结果时，由生产者物化一次并传不可变紧凑快照，禁止各自整行重载或在 Celery 消息中复制数据库审计载荷。
- 同一工作流阶段调用多个子服务时必须共享一个有界运行上下文；前一个子服务写回后同步更新上下文，后续子服务不得重新加载同一大字段，也不得用旧快照覆盖前一次结果。
- worker 首次读取业务载荷后，成功、失败、取消、验证码和重试收口必须复用有界内存快照并只重查状态列；异常处理器不得为了判断取消状态重新读取 `params/result`。
- 可重试 DB 异常必须保持任务记录为非终态，并以故障注入验证下一次 delivery 确实执行；日志出现 `retry scheduled` 但重试被终态去重，按未修复处理。
- 结构化实体必须同时覆盖命令生产者、命令消费者和终态写回。列表与 watchdog 已轻量化，但执行 worker 仍读 JSON 时，迁移仍视为不完整。
- 阶段轮询必须先查询结构化状态 `Row/DTO`。大字段只允许在终态收口、明确异常恢复或旧数据兼容时按命中主键读取一次；轮询中的 `query(...).all()` 不得返回热点模型实体。
- `load_only` 必须覆盖下游实际访问的全部属性，并由 SQL 捕获测试验证没有 deferred refresh；仅看到代码里写了投影不算合格。

## 父子任务与重启纪律

- 父工作流进入终态后，所有强绑定子任务必须由统一 reconciler 收口；规则按“父 feature × 子 feature × 父状态”矩阵维护，不能只修现场出现的某一种 feature。
- 新增父工作流、子任务类型或终态时，必须同时补充矩阵契约测试；测试至少覆盖取消/失败父任务、活动子任务和允许继续执行的业务例外。
- 重启脚本必须在停止进程前 fail-closed 检查不可中断任务；检查数据库失败等同于检查失败，不能继续重启。
- 重启预检与孤儿收口职责不同：预检防止制造新孤儿，reconciler 清理历史孤儿；任何一边缺失都不能宣称生命周期问题解决。

## 异常尖峰处理

- 热点只读接口必须有短于 PgBouncer 全局 `query_timeout` 的语句级超时；允许降级的列表/统计接口应保留有界过期快照，数据库瞬时阻塞时不得等待满 120 秒后直接返回 500。
- 若同一 SQL 的现场 `EXPLAIN (ANALYZE, BUFFERS)` 小于 10ms，但业务日志出现秒级或分钟级尖峰，应按运行时阻塞处理：同时核对 PgBouncer timeout、连接等待、锁、写放大、TOAST、autovacuum 和并发任务。
- PgBouncer 连接池验收必须同时核对 `SHOW POOLS` 与 `SHOW SERVERS`。若慢请求复用了长时间无请求的远端 server connection，应保留少量热连接并及时清理超出最小池的陈旧连接；禁止继续用重复索引处理网络连接冷启动或休眠恢复延迟。
- 执行计划已正确命中索引时，禁止继续添加同形重复索引。必须先证明新索引减少了扫描、排序或堆访问。
- 修复异常尖峰必须同时记录“正常执行计划”和“异常运行证据”；只保留其中一侧会再次把连接/写入问题误判为索引问题。
- 结构迁移必须在所有应用连接为 0 时执行。迁移脚本应在事务起点检查连接并 fail closed，启动脚本应在进程启动前检查 schema、权限、回填和索引。
- 遇到“多条原本亚毫秒的不同查询在同一秒一起变慢”，优先检查 `pg_stat_activity/pg_locks` 和当时 DDL；禁止分别给每条查询补索引。

## 入库与载荷纪律

- 新增会参与列表、过滤、关联、去重、重试或产物定位的 JSON 字段时，必须同步定义结构化投影列、入库维护者、历史回填和索引；不得只优化查询端。
- ORM `before_insert/before_update` 钩子只能读取已加载属性；读取其他属性前必须检查 SQLAlchemy state，禁止在 flush 阶段触发隐式 SELECT。
- `load_only` 查询禁止继续调用旧式 `Query.get()`；主键读取使用显式过滤或统一投影助手。
- 列表和轮询不得返回完整堆栈、日志数组或无限增长文本。必须设置字符/行数预算，完整内容留在详情、事件表或文件中。
- `EXPLAIN ANALYZE` 只证明数据库执行时间；还必须测量返回行数、估算字节数和客户端端到端耗时，防止“计划 0.3ms、传输 1.5s”的误判。
- 下游需要按批次消费文件、附件、产物或子任务集合时，源事务必须同时写入结构化关系表；审计 JSON 不能作为热路径中唯一的集合索引。
- 热循环必须同时定义列预算和次数预算：默认每页一次集合查询，禁止按 topic、附件或子任务逐条点查；同一阶段刚写入的数据必须通过 Row/DTO 快照交给下一步，禁止立即按相同条件重查。
- 涉及 `load_only` 的更新路径必须用 SQL 捕获测试覆盖 flush/commit，防止 mapper 钩子绕过投影预算。
- 新结构必须覆盖 ORM 事件、bulk UPDATE、原生 SQL 和重试补写等所有入库方式。只验证模型钩子、只改读取端或只回填历史数据均不合格。
- 原子 JSON/JSONB patch 改变投影来源时，必须在同一数据库语句中从合并后的 payload 计算结构化列；禁止依赖不会触发的 ORM mapper 事件。
- 数据修复脚本不得假设主键或数组参数类型；必须依据模型/数据库契约写显式类型测试，并在提交后执行同一审计确认剩余不一致为 0。
- 历史 JSON 兼容回退必须有可验证的覆盖判据。结构化台账完整后，即使目标类型为空或磁盘文件缺失，也不得重新读取大 JSON。
- 服务引用新增列或表前必须有显式 schema/权限检查并给出唯一迁移脚本；禁止让缺失迁移表现为通用“数据库操作失败”。

## `publication_tasks` P0 专项门槛

`publication_tasks` 是跨工作流共享热点表，按 P0 架构债管理，不再等待用户反馈后人工翻日志：

- 所有进程把该表超过 500ms 的 SQL、失败 SQL、JSON 条件查询和批量 `params/result` 读取写入 `logs/publication_tasks_query.log`。
- 专项日志必须包含 SQL 指纹、分类、耗时、PID、进程启动时间和真实代码位置；复查使用 `scripts/dev/analyze-publication-task-queries.py` 聚合，不按参数值重复计数。
- 部署后验收窗口内，`json_predicate` 和 `multirow_payload` 分类必须为 0；出现 1 条即重新打开问题，不能以平均耗时尚可为由放行。
- 进度回调产生的 `slow_payload_write` 必须为 0；终态单次 JSON 写入可以保留，但持续进度写入一经出现即重新打开问题。
- 单行详情允许按主键读取完整载荷，但超过 500ms 的 `slow_payload` 必须继续拆分或迁移；列表、轮询、watchdog、缓存匹配不得读取完整载荷。
- 新结构发布必须同时覆盖入库同步、历史回填、索引、读取切换和至少两个业务入口的契约测试。只改查询端或只回填历史数据均不合格。
- 日志中的 PID 启动时间早于代码部署边界时，只能判定为旧进程未重启；在新 PID 产生真实样本前，状态保持“代码已修改”或“已部署待验收”。
- 同一 SQL 指纹再次出现时必须关联既有 Bug 记录；不得新开一轮相同的临时补丁并重置完成口径。
- 父子等待类修复必须在真实延迟续跑样本中验收：确认父/子载荷指纹为 0、旧代次消息 no-op、最新消息继续调度、终态结果完整。只验证首次执行不合格。
- `multirow_payload` 是查询形状失败，不受 1 秒慢查询阈值豁免；哪怕当前只有几十毫秒，也必须重新打开对应 P0 问题并追到代码入口。

## 运行验收模板

```text
修复前：<时间窗口> / <SQL 指纹> / <次数、P95、最大值>
部署边界：<进程角色> / <PID> / <启动时间>
修复后：<真实业务批次> / <次数、P95、最大值>
业务完整性：<状态、产物、通知、重试结果>
结论：已定位 | 代码已修改 | 已部署待验收 | 已解决
残余项：<未覆盖内容>
```
