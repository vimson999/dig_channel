# 成功经验复用纪律

本文档约定：项目内新增功能、修复 bug、扩展编排或 worker 时，必须优先复用已经验证过的成功模式。目标是停止重复踩同一类坑，把历史故障和成熟实现变成默认工程约束。

## 适用范围

满足任一条件时，必须执行本文档：

- 新增或改造编排任务。
- 新增 Celery worker、scheduler、watchdog、清理任务。
- 接入浏览器自动化、外部平台、Gemini、豆包、知识星球、发布链路。
- 处理数据库连接、长等待、父子任务、失败续跑、任务状态、邮件通知。
- 用户明确指出“已有功能是好的，为什么这里不一样”。

## 核心原则

1. 先找成熟实现，再写新代码。
2. 复用不是只复用函数；必须复用完整行为契约。
3. 新功能默认对齐最稳的现有链路，而不是从空白开始。
4. 如果选择不复用，必须在设计或 bug 记录里写明原因和风险。
5. 已经发生过的事故，必须转化为检查项，不允许靠记忆。

## 前置检查

开始实现前必须回答：

- 这个需求是否已有相似成功功能？
- 成功功能的入口、API、worker、service、frontend、测试分别在哪？
- 它的稳定性靠哪些机制保证？
- 新功能是否复用了这些机制，而不只是复用了底层调用？
- 如果不复用，是否会丢掉重试、幂等、续跑、观测、通知或资源保护？

常用检索命令：

```bash
rg -n "FEATURE_NAME|process_.*workflow|retry|child_attempts|retry_state|waiting_child|deferred_waits|workflow_notification|guard_publication_task_start" src/backend
rg -n "失败续跑|reused|retry|children|progress|status" src/frontend docs
```

## 必须复用的经验类型

### 编排与父子任务

复用范围必须包括：

- 父任务 `PublicationTask` 的 `params/result` 结构。
- `result.children` 子任务摘要。
- `result.child_attempts` 和 `result.retry_state` 尝试记录。
- 可重试错误识别。
- 子任务失败后的自动重试或延迟恢复。
- 父任务终态对子任务的收口。
- 失败续跑时复用已完成且产物完整的节点。

反例：

- 只复用同一个 worker，但外层父编排没有复用重试和恢复策略。
- 只复用产物生成函数，但没有复用产物完整性校验。

### 数据库与长等待

复用范围必须包括：

- 按进程角色配置连接池。
- 长等待期间释放数据库 session。
- 等待后重新按 ID 加载 ORM 对象。
- 对瞬断、连接池耗尽、服务端断开做有限重试。
- 对重任务优先采用状态机 + 恢复调度，而不是父 worker 长时间占坑。
- 后台循环、看门狗、scheduler、CLI 和只读监控 API 必须遵守 [数据库 Session 生命周期纪律](database-session-lifecycle-discipline.md)。
- 检查 `idle` 与 `idle in transaction` 的区别：允许受控 `idle`，不允许长期 `idle in transaction`。

反例：

- 认为“只是查询状态”就不释放 session。
- 只在外层循环释放 session，但 DB 查询后继续做 Redis、进程扫描、文件 IO，导致事务在本轮内被挂住。
- 复制成熟功能的页面和 API，却漏掉它的 session 释放、结果瘦身、失败续跑或状态收口。

### 浏览器自动化

复用范围必须包括：

- 同类平台的上传、提交、等待、回收策略。
- 可恢复错误的重试策略。
- 失败日志、截图或步骤日志。
- 防止旧浏览器任务遗留 active 状态。

### Worker、scheduler 与 watchdog

复用范围必须包括：

- `scripts/dev/run-celery-*.sh` 和 `stop-celery-*.sh`。
- Celery Monitor 服务表。
- backend bootstrap 启动守护。
- watchdog 自动恢复或收口规则。
- 业务 active 状态与 Celery runtime 的对账逻辑。

### 前端页面

复用范围必须包括：

- 列表筛选、搜索、分页、排序。
- 状态 pill、进度条、失败续跑、取消、复制、预览。
- API base、错误提示、缓存版本号策略。
- 与成熟页面一致的数据字段命名和展示逻辑。

## 实施流程

1. 先在代码和文档中找相似功能。
2. 列出成熟功能的稳定性机制。
3. 明确本次实现会复用哪些文件、函数、状态字段和测试。
4. 只在差异点上新增代码。
5. 验证时同时验证新功能和被复用契约。
6. 如果踩到新坑，按 bug 纪律新增记录，并反向更新本纪律或相关标准。

## 设计记录要求

涉及新功能或较大修复时，设计说明必须包含：

- 参考的成功实现。
- 复用的能力清单。
- 未复用项和原因。
- 对齐后的验收项。

示例：

```markdown
## 成功经验复用

- 参考实现：`report_audio_workflow`
- 复用能力：
  - Gemini 子任务自动重试
  - `child_attempts/retry_state`
  - 等待子任务时重新加载 ORM 对象
  - 失败续跑复用已完成节点
- 未复用项：
  - 豆包 TTS 分段，因为本功能不涉及音频朗读
- 验收：
  - 子任务瞬时失败不会直接失败父编排
  - 页面可看到重试轨迹
```

## 评审检查清单

提交前必须检查：

- 是否搜索过相似成熟实现。
- 是否说明复用边界。
- 是否复用了重试、幂等、续跑、观测、通知。
- 是否补齐 worker/scheduler/watchdog/monitor 的注册。
- 是否更新相关文档、bug 记录或标准。
- 是否跑过能证明复用契约有效的测试或现场验证。

## 复发处理

如果后续再次出现“已有功能稳定，新功能漏掉同类保护”的问题：

- 必须补 bug 记录。
- 必须补充本文档或对应专项标准。
- 必须检查同类新功能是否也漏掉该成功经验。
- 不能只修当前点位。
