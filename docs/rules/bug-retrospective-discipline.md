# Bug 定期回顾与复发升级纪律

本文档把单条 Bug 记录升级为持续的系统性治理。目标不是统计数量，而是识别同一根因是否换了模块再次出现，并在第二次复发时停止局部打补丁。

## 回顾触发条件

满足任一条件必须进行正式回顾：

- 距离上次正式回顾满 7 天且期间新增过 Bug。
- 上次回顾后新增 5 条 Bug，以先到者为准。
- 任一 `复发键` 出现第二次，不等待固定周期，立即回顾。
- 出现数据丢失、误报成功、数据库不可用、核心编排停摆等 P0 事故。

正式回顾写入 `docs/bugs/reviews/YYYY-MM-DD-主题.md`，并更新 `docs/bugs/recurrence-registry.json`。

## 每条 Bug 的复发元数据

新增 Bug 记录必须包含：

- `根因分类`：稳定的工程域，例如 DB Session、父子任务状态机、热点查询、外部调用、产物校验。
- `复发键`：同一技术根因使用同一个稳定 key，例如 `DB-SESSION-LIFECYCLE`。
- `是否复发`：首次、第二次或第 N 次。
- `关联记录`：至少链接已知同根因记录。
- `防线层级`：`local_patch`、`shared_guardrail`、`contract_test`、`observability` 中已落地的层级。

不能确认分类时先进入 `standalone_records`，并写明重点观察项；后续再次出现相同症状时必须合并为复发根因簇。

## 复发升级规则

### 第一次出现

- 修复当前根因。
- 增加能稳定复现该问题的测试。
- 记录监控或现场验证方法。

### 第二次出现

- 不允许只修当前入口。
- 必须横向检查所有同类工作流和 worker。
- 必须抽取共享防线或共享状态契约。
- 必须增加至少两个不同业务入口的契约测试。
- 在 `recurrence-registry.json` 中登记为复发簇，并进入路线图。

### 第三次及以上

- 自动升为 P0 架构债。
- 相关模块暂停继续复制同类实现，直到共享防线落地。
- 验收必须包含历史事故回放、跨模块测试和运行态观测。
- “修改规则文档”不能单独作为完成条件。

## 正式回顾内容

每次回顾至少回答：

1. 本周期新增了哪些 Bug，哪些属于已知复发键。
2. 哪些局部修复仍未升级成共享防线。
3. 哪些通用修复影响了合法业务场景，存在过度收口风险。
4. 哪些规则只有文档，没有自动测试或运行时指标。
5. 下周期必须关闭的 P0/P1 系统性措施及验收标准。

## 完成定义

复发问题只有同时满足以下条件才可标记为系统性关闭：

- 共享实现或统一状态契约已落地。
- 至少两个代表性业务入口通过契约测试。
- 历史 Bug 场景能够自动回放。
- 运行时能发现再次违反不变量的情况。
- 相关根因簇在连续两个回顾周期内没有新增同类事故。

单个历史任务被人工修好、状态被手动回正、或者新增一条 allowlist，都不算系统性关闭。

## 执行检查

```bash
./venv/bin/python scripts/dev/review_bug_records.py --strict
./venv/bin/python -m unittest tests.unit.test_bug_review_discipline
```

检查器保证：

- 每条 Bug 都被归入复发根因簇或独立观察事件。
- 根因簇至少包含两条记录，并声明系统性防线。
- 正式回顾与最新 Bug 之间不会超过约定周期。
